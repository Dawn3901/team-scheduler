# AI 约束 04 · 变更控制与追踪

版本：v1.0  
日期：2026-10-27  
适用：项目组、AI 编码助手  
目的：6 周项目最大的风险不是“不会做”，而是**范围蔓延、契约漂移、文档与代码不一致**。本文规定“想改”怎么变成“可追溯的改”。

---

## 1. 为什么需要变更控制

- 6 周时间固定，加一个需求就必须砍一个需求。
- 三端 + 2 人 + AI，任何契约变更都会同时影响前端、后端、测试、演示；没有第三人兜底，变更必须两人确认。
- AI 很容易“顺手做得更完整”；没有 CR，就会在最后一周发现范围失控。
- 答辩时老师会问“为什么没做 X”；有 CR/ADR 能说清“评估过、取舍了”。

**原则：先记录，再决定，后实施；不允许静默变更。**

---

## 2. 冻结项

| 冻结项 | 时间 | 变更方式 |
|---|---|---|
| 产品范围（P0/P1/不做） | 2026-10-27 | CR + 两人批准 |
| API 路径/字段/错误码 | W1 周五 | CR + 前后端确认 + 契约测试 |
| 数据表/列/枚举/索引 | W2 周五 | CR + ADR + 迁移 + 备份 |
| WS 消息类型 | W3 周五 | CR + 前后端 + 文档 |
| 演示脚本 | W5 周五 | 只修 bug，不加功能 |

冻结不是“不能改”，而是“不能悄悄改”。紧急修复见 §8。

---

## 3. 变更申请（CR）

### 3.1 何时需要 CR

- 新增/删除/降级 P0。
- 新增 P1 并排进本期。
- 改 API 路径/字段/错误码/分页/时间格式。
- 改表/列/枚举/索引/软删除。
- 改 WS 消息类型/payload。
- 改权限模型/私密规则/时区规则。
- 改技术栈/依赖/原生权限/部署方式。
- 改验收标准或演示范围。

不需要 CR：修 bug（不改变契约）、补测试、改文档错别字、内部重构（行为不变）。

### 3.2 CR 模板

```markdown
# CR-00X · <标题>

- 日期：
- 提出人：
- 关联需求：
- 类型：范围 / 接口 / 数据 / 权限 / 技术 / 验收
- 优先级：紧急 / 高 / 中 / 低

## 1. 背景
（现在的问题/机会，为什么不能等到下期）

## 2. 变更内容
（具体改什么；不要写“优化一下”）

## 3. 影响分析
- 范围：新增/删除哪些 P0/P1
- 进度：增加多少人日；从哪周挤
- 数据：表/列/迁移/兼容
- 接口：路径/字段/错误码/前端
- 权限/隐私：是否影响
- 测试：新增/修改哪些用例
- 文档：更新哪些
- 演示：是否影响 8 分钟脚本
- 风险：

## 4. 替代方案
（至少 1 个；说明为什么不做）

## 5. 取舍
（如果做，砍掉什么？如果不做，损失什么？）

## 6. 决策
- 结论：批准 / 拒绝 / 延期
- 批准人（2 人项目组：两人都需同意）：
- 日期：
- 实施负责人/截止：
```

### 3.3 示例：CR-001 加“重复活动”

```text
背景：组会每周一次，手动建 6 次麻烦。
变更：EVT-10 从 P1 提到 P0，支持每周重复，最多 20 次。
影响：+2 人日；需加 recurrence 字段/展开逻辑/编辑单次或整组；前端表单+1；测试+4。
取舍：需把 W5 的 UI 打磨砍 1 人日、W6 缓冲砍 1 人日。
替代：手动建 6 次（0 人日），但演示效果差。
决策：拒绝。理由：6 周内收益低于成本；答辩用“多次创建”演示，P1 记录。
```

> 这个示例说明：**不是所有变更都要接受；拒绝也要记录理由。**

## 4. 架构决策记录（ADR）

### 4.1 何时写 ADR

- 选型/架构变化（如换日历库、加 Redis、改认证）。
- 数据模型重大变化（加表、改主键、改软删除）。
- 权限/隐私模型变化。
- 部署/同步模型变化。

小的字段增减用 CR 即可；ADR 记录“为什么这样设计”。

### 4.2 ADR 模板

```markdown
# ADR-00X · <决策标题>

- 日期：
- 状态：提议 / 已接受 / 已废弃
- 关联 CR：

## 背景
（约束、问题、为什么现在决定）

## 决策
（一句话结论 + 关键细节）

## 备选方案
1. ...
2. ...

## 后果
- 正面：
- 负面：
- 需要后续处理的：

## 验证
（怎么证明这个决策有效；测试/演示/指标）
```

### 4.3 已有决策

框架中的 D1–D15、Q1–Q6 已经是一次“批量 ADR”。不要重复写；后续变更引用它们，例如“修改 D3 需 ADR-003”。

## 5. 影响分析清单

每次 CR 必须逐项回答：

- [ ] 影响哪些需求编号？新增/删除/降级？
- [ ] 影响哪几周？增加多少人日？从哪挤？
- [ ] 影响哪些表/列/索引/迁移？能否兼容旧数据？
- [ ] 影响哪些 API/字段/错误码/前端调用？
- [ ] 影响哪些页面/组件/移动端？
- [ ] 影响权限/私密/时区/提醒？
- [ ] 新增/修改哪些测试？
- [ ] 更新哪些文档（00/02/03/ai/README）？
- [ ] 是否影响 8 分钟演示？
- [ ] 最坏情况是什么？如何回滚？

**答不上来 = 还没想清楚，不要批准。**

## 8. 紧急修复

定义：演示前 48 小时内、影响 P0 演示路径的 bug。

流程：

1. 在群里说明：现象、影响、拟修复范围。
2. 只改最小代码；不动契约/表/依赖。
3. 补回归测试（至少 1 条）；跑 `make check`。
4. 1 人快速 review；合并后立即在演示环境验证。
5. 记录到 `docs/进度与验收.md`：时间、原因、修复、验证。
6. 如果必须改契约/表 → 不走紧急通道，按 CR 处理；宁可降级演示。

**禁止**：以“紧急”为名加功能、重构、跳过测试。

---

## 9. 每周审查

每周五复盘加 10 分钟“范围与契约”：

- [ ] 本周有没有未记录的变更？
- [ ] 有没有“先做了再补文档”的？
- [ ] 追踪矩阵是否更新？
- [ ] 有没有 P1 混入 P0？
- [ ] 下周是否有需要提前批准的 CR？
- [ ] 演示脚本是否仍能走通？

发现未记录变更：补 CR/ADR，评估是否回滚；不惩罚提出，惩罚隐瞒。

---

## 10. 版本与归档

- 文档版本：`v1.0` 起；重大变更升 `v1.1`，不覆盖旧版。
- 历史验收记录只追加，不改写。
- CR/ADR 按编号归档在 `docs/changes/`（W1 创建）：
  ```text
  docs/changes/
    CR-001-recurring-events.md
    ADR-001-calendar-library.md
  ```
- 答辩材料引用最终版本；旧版留在 git 历史即可。

---

## 11. AI 规则

- AI 不得自行发起范围变更；只能提出 CR 草案。
- AI 不得在实现中“顺便”改契约；发现需要改，停下来写 CR。
- AI 不得修改已冻结的 `docs/00` 决策；要改，先 ADR。
- AI 不得删除/改写历史 CR/ADR/验收记录。
- AI 提交 PR 时，必须写：关联需求、是否改契约、验证命令、未验证项。
- AI 发现文档与代码冲突，必须报告；不得默认“代码是对的”。

---

## 12. 一句话总结

**想改可以，但要写下来：为什么改、影响什么、砍什么换、谁批准。没有 CR 的变更，就是范围失控的开始。**
