# AI 约束 03 · 提示词与评审模板

版本：v1.0  
日期：2026-10-27  
适用：向 AI 提需求的人、评审 AI 产出的人  
目的：把“帮我做个功能”变成**有边界、有验收、可验证**的任务；把“看起来对”变成**按清单审**。

---

## 1. 使用方式

1. 选模板：功能 / 修 bug / 评审 / 测试 / 文档 / 重构。
2. 填上下文块（§2）——每次都要贴，AI 不共享上一次对话的记忆。
3. 填任务块（§3–§7）。
4. 要求 AI 按 §9 的格式输出。
5. 按 §8 的清单评审；不通过就退回，不要“先合并再说”。

---

## 2. 通用上下文块（复制到每个提示词开头）

```text
项目：TeamSync（同频），团队共享日程 + 轻量任务，2 人课程项目 + AI 辅助，6 周。
开始前必须读：
- AGENTS.md
- docs/00-需求与设计框架-v1.0.md
- docs/02-需求规格说明书.md
- docs/03-概要设计说明书.md
- docs/ai/01-需求与验收约束.md
- docs/ai/02-接口与数据契约.md

硬约束：
- 只做 P0；P1/P2 不做，除非我明确批准。
- 不改 API 字段/错误码/表结构/WS 类型；要改先写 CR。
- 每个团队查询必须 require_member；私密活动服务端脱敏。
- 时间存 UTC；按团队时区显示。
- 不写死密钥/账号；不跳过测试；不做无关重构。
- 跑不了就写“未验证”，不要编造结果。

输出格式：
结论 / 改动 / 验证 / 未验证 / 风险。
```

## 3. 功能开发模板

```text
【任务】实现 <功能名>
【需求编号】<EVT-7>（P0）
【用户故事】
作为 <角色>，我希望 <行为>，以便 <价值>。
【现状】
- 已有：<相关文件/接口/组件>
- 缺少：<具体缺口>
【验收标准】
Given ...
When ...
Then ...
And ...
【范围】
做：
- ...
不做：
- ...（P1/P2）
【涉及】
- API：<方法/路径>（已冻结，不改）
- 表：<表名>（已冻结，不改）
- 页面/组件：<路径>
- 测试：<文件/用例名>
【约束】
- 沿用现有模式；不引入新依赖/框架。
- 不重构无关代码；一个 PR 只做这件事。
- 新增逻辑必须有测试；修 bug 必须有回归用例。
【验证】
- `make check`
- 具体测试：<...>
- 手工路径：<...>
【输出】
按“结论/改动/验证/未验证/风险”回复；附 `git diff --stat`。
```

### 示例（片段）

```text
【任务】活动邀请成员
【需求编号】EVT-7（P0）
【验收标准】
Given 我是团队成员且是活动组织者
When 我提交 participant_ids=[2,3]
Then 2/3 成为参与者，response=pending
And 重复提交同一 id 不报错、不重复插入
And 非团队成员 id 返回 422 INVALID_PARTICIPANT
【不做】
- 邮件邀请、邀请链接、批量导入（P1/P2）
```

## 4. 修 Bug 模板

```text
【Bug】<一句话>
【需求编号】<相关 P0>
【复现步骤】
1. ...
2. ...
【期望】
...
【实际】
...
【环境】
- 端：Web/Electron/Android
- 浏览器/系统：
- 账号/团队：
【日志/截图】
...
【怀疑范围】
- 文件/函数：
- 最近改动：
【要求】
1. 先写一个失败的回归测试（或说明为什么难以自动化）。
2. 修根因，不做“try/except 吞掉”。
3. 不改变 API/表/错误码。
4. 跑 `make check` + 回归测试。
5. 说明是否影响其他端。
【输出】
根因 / 修复 / 测试 / 影响 / 未验证。
```

**禁止**：为了让测试变绿而改测试期望；用 `sleep` 掩盖竞态；把异常吞掉。

## 5. 代码评审模板

```text
【评审对象】<PR/分支/commit>
【关联需求】<编号>
【请按以下顺序审】
1. 需求符合性：是否只做了该做的？有没有多做/少做？
2. 权限：跨团队、角色不足、私密活动详情/忙闲脱敏。
3. 时间：UTC、团队时区、全天、跨天。
4. 错误处理：401/403/404/409/422 是否正确；前端是否有提示。
5. 数据：迁移可跑；索引；软删除过滤；N+1。
6. 测试：新增/修改是否有覆盖；有没有 skip/改期望。
7. 安全：密钥、日志、注入、XSS、CORS。
8. UI：加载/空/错误/移动端/键盘。
9. 文档：API/表/命令/追踪矩阵是否更新。
10. 可维护性：是否引入第二套模式；命名是否清晰。
【输出格式】
| 严重级别 | 文件:行 | 问题 | 建议 |
| P0 | ... | ... | ... |
| P1 | ... | ... | ... |
| Nit | ... | ... | ... |
结论：通过 / 需修改 / 拒绝
必须修复：...
可以后续：...
```

严重级别：

- **P0**：安全/数据/权限/崩溃/需求错误 → 必须修。
- **P1**：边界/错误提示/性能/测试缺失 → 合并前尽量修。
- **Nit**：命名/格式/注释 → 可后续，不阻塞。

## 6. 测试模板

```text
【目标】为 <模块/需求> 补测试
【需求编号】<...>
【必须覆盖】
- 正常路径：
- 边界：空/最大/最小/跨天/时区
- 权限：非成员/角色不足/私密
- 错误：409/422/404
- 幂等：重复邀请/重复提醒
【测试数据】
- 工厂：<...>
- 固定时间：<...>
【要求】
- 不 mock 核心逻辑；只 mock 外部（WS/邮件）。
- 断言可观察结果，不断言内部实现。
- 测试名能看出需求：`test_private_event_masked_in_availability`。
【验证】
- `pytest ... -q`
- 覆盖率报告（如适用）
```

## 7. 文档/重构模板

### 文档

```text
【文档】<路径>
【读者】<项目组/教师/AI>
【必须包含】
- 目的与范围
- 与现有文档的关系
- 决策/流程/模板
- 示例
【要求】
- 不复制大段 PRD；用链接。
- 不写未实现的功能为“已完成”。
- 变更记录追加，不改历史。
```

### 重构

```text
【重构】<范围>
【前提】行为不变；API/表/错误码不变。
【步骤】
1. 先补/确认测试全绿。
2. 小步重构；每步跑测试。
3. 不改公共接口；如必须改，先 CR。
【禁止】
- 顺手改需求/UI/文案。
- 批量重命名/格式化整个仓库。
【输出】
行为是否变化 / 测试前后结果 / diff 说明。
```

## 8. 评审清单（打印版）

### 8.1 需求

- [ ] 关联 P0 编号；验收标准逐条覆盖。
- [ ] 没有 P1/P2 混入。
- [ ] 异常路径（403/404/409/422）有处理。
- [ ] 文案/交互与 PRD 一致。

### 8.2 权限与隐私

- [ ] 所有团队路由有 `require_member`。
- [ ] 资源按 id 取时校验 `team_id`。
- [ ] 非成员 404；角色不足 403。
- [ ] 私密活动详情 404；忙闲脱敏；冲突脱敏。
- [ ] 通知只能本人读。

### 8.3 时间

- [ ] 存 UTC；API 带 `Z`。
- [ ] 全天 `end_at` 是次日 00:00。
- [ ] 跨天/跨月/23:30 有测试。
- [ ] 前端按团队时区显示，不手加 8 小时。

### 8.4 数据

- [ ] 迁移可从空库/旧库跑。
- [ ] 索引覆盖查询。
- [ ] 软删除过滤。
- [ ] 无 N+1。
- [ ] 唯一约束/幂等。

### 8.5 错误与安全

- [ ] 错误码与契约一致。
- [ ] 不泄露堆栈/SQL/敏感字段。
- [ ] 日志不含 token/密码。
- [ ] 输入校验（长度/枚举/时间）。
- [ ] 无密钥/`.env` 入库。

### 8.6 测试

- [ ] 新增/修改有测试。
- [ ] 修 bug 有回归用例。
- [ ] 没有 skip/改期望/删断言。
- [ ] `make check` 全绿。

### 8.7 前端

- [ ] 加载/空/错误状态。
- [ ] 移动端 375px 可用。
- [ ] 键盘可达；按钮有 `aria-label`。
- [ ] 不白屏；错误可重试。
- [ ] 不在组件里写业务规则。

### 8.8 文档

- [ ] API/表/WS 变更已更新 `docs/03`。
- [ ] 契约变更已更新 `docs/ai/02`。
- [ ] 追踪矩阵已更新。
- [ ] 命令/README 已更新。

## 9. AI 输出契约

每次任务结束，必须按以下格式：

```text
结论：完成 / 部分完成 / 失败
需求：<编号>
改动：
- <path>: <为什么>
验证：
- `命令` → 通过/失败（贴关键输出或摘要）
- 手工：<步骤> → <结果>
未验证：
- <需要人工/真机/部署确认的部分>
风险/后续：
- <已知限制/待办/需要决策>
```

**规则**：

- 没跑的命令写“未运行”，不要写“通过”。
- 失败就写失败，附错误摘要；不要藏。
- 未验证要具体（“Android 通知需真机确认”），不要写“应该没问题”。
- 风险要可行动（“需要产品确认是否允许组织者拒绝”），不要写“可能有风险”。

## 10. 什么时候必须停下来

出现以下任一情况，AI 应停止实现并提问：

1. 需求编号不存在/验收标准矛盾。
2. 需要改 API/表/错误码/WS。
3. 需要新增依赖/框架/原生权限。
4. 发现现有代码与文档冲突。
5. 测试失败原因不明，且修复需要改契约。
6. 发现密钥/个人信息/不安全实践。
7. 任务范围超出 1 个 PR 能审的程度。
8. 用户要求“顺便”做 P1/P2。

**停下来问，比猜着做完更专业。**

## 11. 坏提示词 vs 好提示词

| 坏 | 为什么 | 好 |
|---|---|---|
| “做个日历” | 没有范围/验收/端 | “实现 CAL-2 周视图：7×24 网格，跨天分段，移动端横滑；用 react-big-calendar；验收 Given/When/Then…” |
| “把冲突处理一下” | 没说警告还是阻止 | “实现 EVT-11/12：409 + conflicts；ignore_conflicts 可强制；编辑排除自身；补 2 条测试” |
| “优化一下性能” | 没有指标 | “月视图查询 p95 < 300ms；种子 1 万活动；先加索引，不加缓存” |
| “修一下通知” | 没有复现 | “Bug：同一提醒重复 3 条；复现步骤…；期望 dedupe_key 唯一；先写失败测试” |
| “顺便加个评论” | 范围蔓延 | “评论是 P1，不做；如要做，写 CR 并说明砍掉哪项 P0” |

---

## 12. 一句话总结

**提示词给边界，评审按清单，输出要证据；AI 不是“多写点就好”，而是“在契约内做对、可验证”。**
