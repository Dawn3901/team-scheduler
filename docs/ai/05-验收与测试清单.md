# AI 约束 05 · 验收与测试清单

版本：v1.0  
日期：2026-10-27  
适用：项目组、AI 编码助手、验收人  
目的：把“做完了”变成**可复现的证据**。没有证据的完成，不算完成。

---

## 1. 验收策略

| 层级 | 必须 | 证据 |
|---|---|---|
| 自动测试 | W5 前全绿 | 命令 + 输出摘要 |
| 接口/权限 | 每个 P0 模块至少 1 条 | pytest 用例名 |
| E2E | 3 条主流程 | Playwright 报告/录屏 |
| 三端手工 | Electron/Android/移动端 Web | 清单打勾 + 截图 |
| 演示 | 8 分钟脚本跑 2 遍 | 彩排记录 |
| 文档 | PRD/设计/部署/用户手册 | 文件链接 |

**规则**：

- 不能拿“截图看起来对”代替测试；也不能拿“测试过了”代替手工真机。
- 未验证的项写“未验证”，不要写“应该可以”。
- 验收人随机抽查，不复用开发者的同一台机器/同一份数据。

## 2. 命令

> W1 工程建立后生效；未建立的命令写“未建立”。

```bash
# 全量
make check

# 后端
cd server && pytest -q
cd server && pytest tests/test_conflict.py -q
cd server && pytest --cov=app --cov-report=term-missing

# 前端
pnpm -r typecheck
pnpm -r lint
pnpm --filter web test
pnpm --filter web test:e2e

# 数据库
cd server && alembic upgrade head
cd server && alembic downgrade -1 && alembic upgrade head

# 种子/压测
make seed
python scripts/bench.py

# 三端
pnpm --filter web build
pnpm --filter desktop build
npx cap sync android && cd apps/mobile/android && ./gradlew assembleDebug
```

## 4. 前端/E2E

### 4.1 E2E 场景

```text
E2E-01 注册→建队→加入→建活动→邀请→RSVP
E2E-02 忙闲→冲突提示→强制保存
E2E-03 任务指派→完成→状态/截止行
```

### 4.2 组件测试

- 登录表单：空/短密码/重复用户名错误。
- 活动表单：结束早于开始、全天切换。
- RSVP 按钮：当前状态高亮；点击后更新。
- 冲突弹窗：显示冲突人；“仍然创建”触发重试。
- 任务列表：逾期红色；完成变绿。
- 通知角标：未读数。

### 4.3 响应式

- 375px：月视图不横向溢出；周视图可横滑；底部导航可用。
- 768px：侧栏/日历布局正常。
- 1440px：日历不拉伸变形。

## 7. 8 分钟演示脚本

> 演示前 10 分钟：重置种子数据、登录 3 个演示账号、关闭无关通知、确认网络。  
> 项目组只有 2 人；演示团队用 3 个账号（`lin`/`chen`/`wang`）只是为了展示多成员 RSVP，不代表项目组人数。

| 时间 | 步骤 | 期望 | 兜底 |
|---|---|---|---|
| 0:00–0:40 | 背景：群里约时间/口头 RSVP/任务漏截止 | 讲清三个痛点 | 幻灯片 |
| 0:40–1:10 | 三端形态：Web/桌面/Android | 一句话各端定位 | 截图 |
| 1:10–2:20 | 注册 A；建队；B/C 用邀请码加入 | 成员列表出现 3 人 | 预建账号 |
| 2:20–3:40 | 周视图看忙闲；给忙碌的 B 建活动 | 冲突弹窗；改时间或强制保存 | 录屏 |
| 3:40–4:50 | 邀请 B/C；B 接受、C 待定 | A 详情看到 RSVP | 预置数据 |
| 4:50–5:40 | B 端实时收到活动；通知角标 | 2 秒内出现 | 刷新兜底 |
| 5:40–6:30 | A 建任务指派 B；B 完成 | 任务变绿；日历截止行 | 预置任务 |
| 6:30–7:20 | 事件前 15 分钟提醒：桌面通知 + Android 本地通知 | 两端弹出 | 录屏 |
| 7:20–8:00 | 设计与难点：多租户、私密脱敏、时区、三端取舍 | 讲清“为什么不做” | 幻灯片 |

**讲解要点**：

- 强调“服务器权威、HTTP 唯一数据源、WS 只加速”。
- 强调“私密活动忙闲可见但详情不可见”的隐私设计。
- 强调“三端是一套功能 + 三个壳”，不是三套 UI。
- 主动说已知限制：无离线写、无 Android 后台推送、无重复活动。

## 8. 缺陷等级与退出标准

| 等级 | 定义 | 例子 | 处理 |
|---|---|---|---|
| P0 | 演示阻塞/数据泄露/崩溃 | 登录失败、跨团队可读、私密标题泄露 | 必须修 |
| P1 | 核心功能可用但体验/边界有问题 | 某端通知不弹、移动端溢出 | 尽量修；记录 |
| P2 | 非核心/文案/样式 | 图标错位、文案错别字 | 可答辩后 |

**退出标准**：

- P0 = 0。
- P1 有记录且不影响演示；或经指导教师同意。
- 验收清单 P0 通过率 ≥ 90%，剩余项有书面说明。
- E2E 3 条通过；三端手工清单核心项通过。
- 部署可从零启动；种子可重置；备份可恢复。

## 11. AI 规则

- 不许伪造测试结果；必须贴命令与关键输出。
- 不许用“手动点了一下”代替可复现测试；手工项要写步骤。
- 不许跳过/删除失败测试来变绿。
- 不许把“未验证”写成“已验证”。
- 发现测试环境与文档不一致，先报告，不要改文档迁就代码。
- 验收清单由人类验收人打勾；AI 只能提供证据，不能自己宣布通过，也不能替人签字。
- 2 人项目组：每个验收项至少由**非实现者**复核；关键路径两人都签字。

## 12. 一句话总结

**验收不是“我觉得可以”，而是“命令跑过、用例覆盖、三端看过、演示走过”。证据不到，完成不到。**
