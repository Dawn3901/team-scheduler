# AI 约束 01 · 需求与验收约束

版本：v1.0  
日期：2026-10-27  
适用：2 人项目组 + AI 编码助手  
目的：防止 AI **加戏、漏做、把 P1 当 P0、用“更完整”替代验收**。

---

## 1. 权威顺序

当文档/代码/口头说法冲突时，按以下顺序判断：

1. `docs/00-需求与设计框架-v1.0.md` 中已冻结的决策（Q1–Q6、D1–D15）。
2. `docs/02-需求规格说明书.md` 中的需求编号、优先级、验收标准、业务规则。
3. `docs/03-概要设计说明书.md` 中的接口、表结构、算法。
4. 现有代码与测试（它们可能落后于文档，发现冲突要报告，不要默认代码对）。
5. 聊天中的口头补充（必须落成 CR 才算数）。

**冲突时停下来问，不要自己选一个继续写。**

---

## 2. 需求编号是唯一入口

### 2.1 规则

- 没有需求编号的任务，不写代码。
- 每个 PR/提交至少关联一个 P0 编号，例如 `EVT-7`、`AVAIL-4`。
- 一个任务可以关联多个编号，但必须能说清主编号。
- 新增需求先分配编号、写进 PRD、走 CR；不在代码里“先实现再补文档”。

### 2.2 优先级

| 优先级 | 含义 | AI 可以做什么 |
|---|---|---|
| P0 | 6 周必须交付、必须验收 | 直接实现；按 PRD 验收 |
| P1 | 有余力再做 | **默认不做**；需要用户明确说“现在做 P1-xxx”并走 CR |
| P2 | 明确不做 | 拒绝实现；建议记录为未来工作 |

**“顺手做一下”不是批准。** 任何 P1 都需要明确的“做/不做”决定，并说明砍掉什么来换。

---

## 3. 验收标准格式

### 3.1 必须可观察

每条验收标准必须能回答：**谁、在什么前置条件下、做什么、看到什么**。

推荐格式：

```text
Given <前置条件>
When <动作>
Then <可观察结果>
```

示例（`AVAIL-4`）：

```text
Given B 与 A 同团队，B 不是私密活动 P 的组织者/参与者
When B 请求团队忙闲
Then B 看到 P 的时间段 busy=true
And 响应中 title 为 null、event_id 为 null
And 响应中不包含 location/description
```

### 3.2 不接受的标准

| 模糊说法 | 为什么不接受 | 改成 |
|---|---|---|
| “支持私密活动” | 没说谁能看什么 | “非参与者详情 404；忙闲只看到忙碌块” |
| “冲突提示做好” | 没说提示什么、是否阻止 | “409 + conflicts 列表；可 ignore_conflicts 强制保存” |
| “移动端适配” | 没说什么宽度、什么页面 | “375px 宽月视图不横向溢出；周视图可横滑” |
| “通知正常” | 没说触发条件、去重 | “事件前 15 分钟；dedupe_key 唯一；只生成一条” |
| “性能 OK” | 没有数字 | “50 成员/1 万活动，月视图 p95 < 300ms” |

### 3.3 验收证据

- 自动测试：命令 + 用例名 + 通过结果。
- 手工测试：步骤 + 实际结果 + 截图/录屏（如需要）。
- 演示：按 `docs/ai/05-验收与测试清单.md` 的脚本走一遍。

**没有证据 = 没做。**

## 4. Definition of Ready（任务开始前）

一个任务可以开始，必须满足：

- [ ] 有 P0 需求编号。
- [ ] 验收标准可观察（Given/When/Then 或等价）。
- [ ] 明确涉及的表/接口/页面。
- [ ] 明确不做什么（范围外）。
- [ ] 有测试计划（至少列出要覆盖的用例）。
- [ ] 有负责人/截止时间（看板）。
- [ ] 依赖已满足（API/表/设计已冻结）。

不满足时，AI 应该先补齐或提问，而不是“先写起来”。

---

## 5. Definition of Done（任务结束前）

- [ ] 代码实现与 PRD 一致；没有多做/少做。
- [ ] 新增/修改逻辑有测试；修 bug 有回归用例。
- [ ] `make check` 全绿。
- [ ] 权限/私密/时区/冲突/提醒有专项测试。
- [ ] API/DB 变更已更新文档 + 迁移。
- [ ] 演示路径可走通（至少本地）。
- [ ] 没有 P1 混入。
- [ ] 报告写清改动、验证、未验证、风险。

---

## 6. 歧义处理协议

遇到不确定时，按顺序：

1. **查文档**：`00` 决策、`02` 需求、`03` 设计、`AGENTS.md`。
2. **查现有实现**：相邻模块怎么做的；是否有测试表达意图。
3. **写出假设**：如果必须继续，先在回复里写“我假设 X；如果不对请纠正”，并把它标为风险。
4. **停下来问**：涉及以下任一情况，必须问，不能猜：
   - 新增/删除 P0；
   - 改表/改接口/改错误码；
   - 权限/私密/时区规则；
   - 删除/重命名已有功能；
   - 引入新依赖/框架；
   - 验收标准互相矛盾。

**“为了不打扰用户而自行决定”不是理由。**

## 7. 常见“加戏”与正确回应

| 用户/AI 的想法 | 判定 | 正确回应 |
|---|---|---|
| 加评论/附件 | P1 | “评论/附件在 P1，不在本期；如现在做，需要 CR 并砍掉等量 P0。” |
| 加重复活动 | P1 | “EVT-10 是 P1；MVP 用多次创建替代。” |
| 加多负责人 | P1 | “TASK-10 是 P1；MVP 单负责人。” |
| 加离线写 | P2 | “明确不做；服务器权威。” |
| 加 Android 后台推送 | P1 | “MVP 用本地定时通知；前台服务是 P1。” |
| 加导出 .ics | P1 | “P1；答辩不依赖。” |
| 加暗色模式 | P1 | “P1；先保证对比度与可读性。” |
| 加管理员后台 | P2 | “不做；成员/角色页面已够。” |
| 把 404 改 403 让前端好写 | 契约变更 | “不改；前端按 404 处理。需要改走 CR。” |
| 把任务截止日改成可选 | 需求变更 | “PRD 规定必填；要改先改 PRD/表/测试。” |
| 为了让演示通过写死数据 | 违规 | “禁止；用种子脚本。” |
| 跳过失败测试 | 违规 | “禁止；修实现或说明为什么测试错，并让 reviewer 确认。” |

每个功能合并后，更新以下矩阵（可放 `docs/进度与验收.md`）：

| 需求 | 设计 | 代码 | 测试 | 演示 | 状态 |
|---|---|---|---|---|---|
| EVT-7 | 03 §5.4 | `routers/events.py` | `test_event_invite` | 演示步骤 3 | ✅ |
| AVAIL-4 | 03 §6.2 | `services/availability.py` | `test_private_masking` | 演示步骤 3 | ✅ |
| TASK-7 | 03 §5.6 | `routers/tasks.py` | `test_task_overdue` | 演示步骤 5 | ⬜ |

**没有测试/演示证据的，不得标 ✅。**

## 9. 评审时的需求检查

- [ ] PR 关联的编号是否存在、是否 P0。
- [ ] 实现是否覆盖该编号的全部验收标准。
- [ ] 是否多做了未列出的行为（尤其是 P1）。
- [ ] 是否少做了异常路径（403/404/409/422）。
- [ ] 是否改了未在 PRD 中的字段/接口/表。
- [ ] 是否有对应测试，测试名能否看出需求。
- [ ] 文档/追踪矩阵是否更新。
- [ ] 2 人项目组：每个验收项由**非实现者**复核；关键路径（认证/权限/脱敏/时区/迁移/冲突/提醒）两人都签字。
- [ ] AI 只能提供证据，不能作为验收人，也不能替人写“通过”。

## 10. AI 回复模板（需求相关）

```text
需求：EVT-7（P0）
理解：组织者可以邀请团队成员；重复邀请幂等；非成员 422。
不做：评论、附件、重复活动（P1/P2）。
实现：
- ...
验收：
- Given ... When ... Then ...
验证：
- `pytest server/tests/test_events.py::test_invite_idempotent` → 通过
未验证：
- 真机通知（需人工）
风险：
- 无
```

---

## 11. 一句话总结

**只做 PRD 里的 P0，用可观察的验收标准证明，用测试和文档留痕；不确定就问，不要用“更完整”代替“做对了”。**
