# CR-004 · 自然语言快速添加（Quick Add）

- 日期：2026-11-02
- 提出人：项目组讨论（AI 起草）
- 关联需求：建议新增 `CAL-11`（自然语言快速添加）
- 依赖：[CR-002 个人日历](CR-002-personal-calendar.md)（个人目标）；团队目标可独立实现
- 类型：范围 / 接口 / 交互
- 优先级：P1（拓展，不阻塞 P0）
- 状态：**待评审**
- 说明：本期做**规则解析 + 预览确认**；LLM/AI 解析不进入本期，另立 CR/ADR。

---

## 1. 背景

用户经常把日程以一段文本形式存在：

```text
11.28 xx测试
12.05 前交实验报告
下周三下午3点 产品评审 1小时
```

手动逐条打开表单创建成本高，尤其是手机端。Quick Add 允许用户粘贴一段文本，系统解析成“草稿”，用户确认后批量创建日程/任务。

**关键原则：解析结果必须预览确认，绝不静默写入。** 解析错日期比没有功能更糟。

---

## 2. 变更内容

### 2.1 目标

- 日历/我的日程增加“快速添加”入口：粘贴文本 → 解析 → 预览/编辑 → 批量创建。
- 支持多行输入，一行一条；支持常见中文日期/时间格式。
- 每条草稿可选择：目标（个人日历/某个团队）、类型（日程/任务）、全天/时间。
- 本期只做**规则解析**；不接 LLM、不上传文本到外部服务。
- 不新增表、不新增 API；复用 CR-002 `/me/events` 和现有团队活动/任务接口。

### 2.2 本期范围

| 项 | 内容 |
|---|---|
| 入口 | 日历页/“我的日程”页的“快速添加”按钮，打开粘贴弹层 |
| 解析 | 纯前端规则解析（`apps/web/src/lib/quickAdd.ts`），复用已有 `date-fns`，不新增依赖 |
| 预览 | 逐条显示标题/日期/时间/类型/目标/警告，可编辑、可删除、可切换目标 |
| 创建 | 用户确认后逐条调用现有接口；个人目标只创建个人日程；团队目标可创建活动或任务 |
| 失败处理 | 单条失败不阻塞其他条；汇总“成功 N 条、失败 M 条”及原因 |
| 限制 | 最多 50 行/4000 字符；超限提示，不截断静默处理 |
| 测试 | 解析单测 + 预览交互测试 + 一条 E2E；不测试 AI |

### 2.3 明确不做（本期）

- **不做 AI/LLM 解析**：不调用外部模型、不把粘贴文本发给第三方；后续单独 CR/ADR。
- **不做循环日程**：“每周一 9:00 高数”本期不展开；提示用户改用 ICS 导入或逐条添加。
- **不做图片/语音/截图识别**：只接受文本粘贴。
- **不做个人任务**：个人目标本期只创建个人日程；DDL 文本若选个人目标，提示改选团队任务或创建为日程。
- **不做自动写入/后台解析**：必须用户确认。
- **不做跨设备同步的解析草稿**：草稿只在当前页面内存中。
- **不做自动去重/自动冲突修复**：有冲突时按现有 409 流程提示，让用户决定。
- **不做第三方插件**：Quick Add 是内置功能，不是插件。

### 2.4 目标与类型矩阵

| 目标 | 日程 | 任务 |
|---|---|---|
| 个人日历（CR-002） | ✅ 创建个人日程 | ❌ 本期不支持个人任务 |
| 团队日历（现有） | ✅ 创建团队活动（默认 `visibility=team`，无额外参与者） | ✅ 创建团队任务（默认负责人=当前用户） |

- 默认目标由入口决定：从“我的日程”进入默认个人；从团队日历进入默认当前团队。
- 文本含“交/提交/截止/DDL/前”等关键词时，默认建议任务；用户可在预览中改回日程。
- 个人目标下的 DDL 文本：显示警告，提供“创建为全天日程”或“切换到团队任务”两个选择，不静默决定。

## 3. 解析规则（v1）

### 3.1 支持的日期

- `11.28`、`11/28`、`11月28日`、`2026-11-28`；
- `今天`、`明天`、`后天`、`下周三`、`周五`（下一次周五）；
- `11.28-11.30`（多天全天日程）；
- 未写年份按当前年；若日期早于今天，显示警告“已过，是否按明年处理”，不静默跨年。

### 3.2 支持的时间

- `14:00`、`14:00-16:00`、`下午3点`、`上午9点半`、`9:00-11:00`；
- 只有开始时间时默认 1 小时；
- 没有时间时默认全天；
- 全天日期结束为次日 00:00（目标时区）；
- 个人目标用用户时区；团队目标用团队时区；统一转 UTC 存储。

### 3.3 标题与清洗

- 去掉日期/时间片段后的剩余文本作为标题；
- 去掉行首项目符号（`-`、`*`、`•`、`1.`）和多余空白；
- 标题为空时标记为“需要补充标题”，不允许直接创建；
- 标题长度沿用现有规则（1–100 字）。

### 3.4 任务识别

- 关键词：`交`、`提交`、`截止`、`DDL`、`前`；
- 任务截止时间：有具体时间用具体时间；只有日期默认当天 23:59（目标时区）；
- 任务标题去掉“前/截止/DDL”等词后保留动作，如“交实验报告”；
- 识别不确定时默认日程，并在预览中让用户切换。

### 3.5 不支持/需要提示的情况

- 循环规则：提示“本期不支持循环，请使用 ICS 导入或逐条添加”；
- 多个日期混在一行：提示拆分或只取第一个，不静默创建多条；
- 无日期：标记“需要日期”，不允许创建；
- 年份歧义/日期已过：显示警告，用户确认后按提示年份处理；
- 无法解析的文本：保留原文，标记“需要手工编辑”。

## 4. 交互流程

```text
点击“快速添加”
  → 粘贴文本
  → 解析
  → 预览列表（每条可编辑/删除/切换目标与类型）
  → 确认创建
  → 结果汇总（成功/失败/冲突）
```

- 预览必须显示解析后的日期时间，而不是只显示原文。
- 解析后默认全选；用户可取消某条。
- 创建前不清理输入；失败时可返回修改重试。
- 创建后提供“撤销本次添加”（仅当前页面会话内，记录已创建 id；离开页面不保证）。
- 冲突：团队活动创建返回 409 时，显示冲突信息，提供“仍然创建”（`ignore_conflicts=true`）或“跳过”；不自动强制保存。

## 5. 技术方案

### 5.1 前端模块

- `apps/web/src/lib/quickAdd.ts`：纯函数 `parseQuickAdd(text, options) → Draft[]`；
- `Draft` 结构：

```ts
type Draft = {
  kind: "event" | "task";
  target: "personal" | { teamId: number };
  title: string;
  start_at: string;      // ISO UTC
  end_at: string;        // ISO UTC
  all_day: boolean;
  warnings: string[];
  needsReview: boolean;
};
```

- 解析器不访问 DOM/网络，便于 Vitest 单测；
- UI 组件 `QuickAddDialog`：textarea、预览列表、编辑、确认；
- 创建时复用现有 API client：
  - 个人日程：`POST /me/events`（CR-002）
  - 团队活动：`POST /teams/{teamId}/events`
  - 团队任务：`POST /teams/{teamId}/tasks`（assignee_id=当前用户）

### 5.2 不新增后端

- 规则解析完全在前端；不需要新 API、不需要新表；
- 创建复用现有接口，因此权限、时区、冲突、私密规则都不绕过；
- 唯一新增的是前端路由/按钮和一个可选的入口开关（见 §7）。

### 5.3 AI 增强（后续，不在本期）

- 如果规则版上线后仍有大量复杂句子，再评估 `QuickAddProvider`：
  - 规则 provider + 可选 LLM provider；
  - LLM 只在服务端调用，key 不进前端；
  - 输入限制、结构化 JSON 输出、服务端校验、默认关闭、不保存原文；
  - 仍然走同一套预览确认，不允许自动写入。
- 该增强需要单独 CR/ADR，涉及外部依赖、费用、隐私和失败降级。

## 7. 替代方案

### A. 保持手工表单（现状）

- 零成本、零风险；但移动端输入成本高，批量日程很痛苦。

### B. 直接上 LLM 解析

- 能处理复杂句子，但不确定、需 API key、隐私与费用问题；没有预览确认时风险更高。
- **不推荐作为第一版**；可作为规则版的后续增强。

### C. 规则解析 + 预览确认（本 CR 推荐）

- 3–4 人日；覆盖常见“日期 + 标题”输入；无外部依赖、可测试、可预测。
- 缺点：复杂句子/循环规则支持有限，需要明确提示。

### D. 只做 ICS 导入（CR-003）

- 适合整学期课表/大量日程；不适合临时一句“11.28 测试”。
- 与 Quick Add 互补，不替代。

### E. 后端 NLP 服务

- 自建解析服务/模型；成本与维护远超课程项目收益。**拒绝**。

---

## 8. 取舍

**如果做：**

- 3–4 人日，无迁移、无新依赖、无后端改动，风险低；
- 显著降低移动端/批量录入成本，演示效果直接；
- 需要接受“规则解析不是万能”，用预览和警告兜底；
- 不承诺循环、复杂长句、图片/语音。

**如果不做：**

- 用户继续手工建日程；核心功能不受影响；
- 可以把时间留给 AVAIL-6/CR-002；
- 但会失去一个低成本、高感知的体验提升。

**建议：**

1. 先做规则版，覆盖“日期 + 标题”“日期 + 时间 + 标题”“多行”三类；
2. 等 CR-002 个人日历可用后，再把个人目标接上；团队目标可以更早做；
3. AI 解析等规则版有真实失败样本后再评估，不预先接 LLM。

## 10. 验收标准

- [ ] 粘贴“11.28 xx测试”能解析为 2026-11-28 全天日程，并在预览中显示。
- [ ] 粘贴多行文本能生成多条草稿；空行/项目符号被忽略。
- [ ] “下周三下午3点 产品评审 1小时”能解析为对应日期 15:00–16:00。
- [ ] “12.05 前交实验报告”在团队目标下建议任务，截止为当天 23:59；用户可改为日程。
- [ ] 无日期/无标题的草稿标记 `needsReview`，不能直接创建。
- [ ] 日期已过/年份缺失有警告，用户确认后才创建。
- [ ] 个人目标只创建个人日程；DDL 文本选择个人目标时有明确提示。
- [ ] 创建逐条执行；单条失败不影响其他条，结果汇总清楚。
- [ ] 团队活动 409 冲突时提供“仍然创建/跳过”，不自动强制保存。
- [ ] 文本不发送到外部服务；不新增依赖。

## 11. 开放问题

1. 默认目标：从团队日历进入默认团队，从“我的日程”进入默认个人，是否足够？
2. 默认类型：无关键词时默认日程，有“交/截止/DDL”默认任务，是否需要更细的规则？
3. 任务截止日默认 23:59 还是 18:00？建议 23:59，预览可改。
4. “撤销本次添加”只保证当前页面会话，是否可接受？如需跨刷新撤销，要加 batch id/新字段。
5. 是否需要解析“每周一”这类循环？建议本期不支持，指向 ICS 导入（CR-003）或后续 CR。
6. AI 解析的触发条件、provider、隐私边界？另立 CR/ADR。
7. 是否需要与冲突检测做预检？当前创建时 409 已够用，预检会多一次查询。
