# ADR-006：团队沟通采用"对象内消息"，不做 IM

日期：2026-11-17。状态：按用户确认的范围实施（CR-016），待 A/B 复核。

## 背景

用户提出三类沟通场景：Leader 全局通告、邀请时对某成员提特别要求、任务上下文说明（要求/完成/阻塞/交接）。

`docs/00 §2.4`、PRD §10 明确把"即时聊天（IM）"列为不做，理由是产品定位是"团队时间协调 + 轻量任务"，一旦引入自由聊天就会与 IM 竞争，并带来未读、@、编辑删除、分页、审核等一整套成本。

## 决策

1. **一个统一消息模型**：`messages(target_type, target_id, kind, body)`，目标为 `event` / `task` / `announcement`。`kind` 只影响展示与通知文案，**不影响可见性**。
2. **可见性只继承对象**：私密活动消息走 `can_view`；任务/通告消息按团队成员。这样"私密活动评论泄露"在结构上不可能发生。
3. **通告是对象，不是广播消息**：`announcements` 有正文、置顶、失效、以及"点我知道了"的 `announcement_acks` 回执；通告下的追问走 messages。
4. **针对个人的要求用参与者备注**（`event_participants.note`，字段级可见性：组织者/Admin 与本人），不引入"定向消息"这种可见性维度。
5. **阻塞不改状态枚举**：`blocker` / `unblock` 消息 + 派生 `waiting_reason`；依赖造成的阻塞仍由既有 `blocked` 表达，UI 合并展示、数据不混。
6. **未读只有一套**：`read_cursors`（对象级读位）驱动收件箱与圆点；通告未读由回执表定义。不新建第二套未读计数。
7. **WS 不扩类型**：写操作后沿用 `calendar.changed` / `notification.created`（只带 team_id），客户端失效重取。

## 后果

- 一期覆盖 A/B/C 三个场景，且新增 4 张表 + 1 列即可，不需要引入新依赖；
- 用户想要"聊天"时，产品会引导到"对象内讨论"或"发通告"，而不是自由频道；
- 若二期要做 `#general` 频道，需要新增游标分页、消息读位与更严格的通知策略，属独立 CR；
- 代价：讨论是平铺的，不支持树形回复与富文本；跨对象（"这几个活动一起说"）没有统一入口，只能各自讨论。
