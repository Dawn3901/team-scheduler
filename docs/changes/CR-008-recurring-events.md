## 1. 背景

周会、组会、课程实验等场景需要重复活动。当前只能手动建多次，改时间要逐条改。

`EVT-10` 已列入 P1，但完整语义很重：

- 只改本次 / 改本次及以后 / 改整个系列；
- 取消某次、例外日期；
- 每次实例的冲突检测、提醒、RSVP；
- 与 ICS 导入、Quick Add、找空闲的交互。

**建议不要一次做完整版。** 本 CR 给出窄范围方案，先满足“每周组会”的主场景。

---

## 2. 变更内容

### 2.1 目标（建议 Phase 1）

- 支持创建每周/每双周重复活动，设置结束日期或重复次数（二选一）。
- 生成未来实例（建议最多 52 次/1 年），每个实例是普通活动行，复用现有冲突/提醒/RSVP。
- 支持：
  - 修改整个系列的时间/地点/标题；
  - 取消某一次；
- 不支持（Phase 2 再评估）：
  - “改本次及以后”；
  - 无限重复；
  - 按工作日/每月第 N 个周几等复杂规则；
  - 拖拽调整单次实例（可先删除再新建）。

### 2.2 明确不做（本期）

- **不做完整 RRULE UI**：只做每周/每双周 + 结束条件。
- **不做“本次及以后”**：需要拆分系列，复杂度和测试量翻倍。
- **不做无限重复**：必须有结束日期/次数。
- **不做重复任务**：只做活动；任务重复另立 CR。
- **不做重复活动导入**：ICS 导入是 CR-003，独立处理。
- **不做跨系列冲突自动重排**：只按实例做现有冲突检测。
- **不做提醒重排算法**：实例本身就是普通活动，提醒按现有扫描。

### 2.3 创建参数

```json
{
  "title": "每周组会",
  "start_at": "2026-11-04T06:00:00Z",
  "end_at": "2026-11-04T07:00:00Z",
  "recurrence": {
    "frequency": "weekly",      // weekly | biweekly
    "until": "2027-01-31",      // 或 count
    "count": null
  }
}
```

- 只支持 `weekly`/`biweekly`；`until` 与 `count` 二选一。
- 时区按团队时区；实例的 `start_at/end_at` 存 UTC。
- 跨 DST 时保持“团队时区同一本地时间”，不是固定 24h 偏移。

### 2.4 编辑/取消语义

| 操作 | 行为 |
|---|---|
| 改整个系列 | 更新系列元数据；未来未开始的实例批量更新；已开始/已结束的实例不动 |
| 取消某次 | 该实例 `status=cancelled`/软删除；不删除系列；后续生成时跳过该日期 |
| 删除整个系列 | 取消未来实例；保留历史实例（可配置） |
| 改单次 | Phase 2；v1 只能取消后单独新建 |

- 已开始的实例不允许改时间/地点（沿用现有规则）。
- 批量改时间要逐实例做冲突检测；有冲突时返回冲突列表，用户确认后再强制保存（复用 `ignore_conflicts`）。

## 3. 数据模型（建议）

新增 `event_series`，`events` 增加 `series_id`/`original_start`：

```sql
CREATE TABLE event_series (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    team_id INTEGER NOT NULL REFERENCES teams(id),
    frequency TEXT NOT NULL,          -- weekly/biweekly
    interval_weeks INTEGER NOT NULL DEFAULT 1,
    until DATE,
    count INTEGER,
    timezone TEXT NOT NULL,
    created_by INTEGER NOT NULL REFERENCES users(id),
    created_at DATETIME NOT NULL,
    updated_at DATETIME NOT NULL,
    deleted_at DATETIME
);

ALTER TABLE events ADD COLUMN series_id INTEGER REFERENCES event_series(id);
ALTER TABLE events ADD COLUMN original_start DATETIME;

CREATE INDEX ix_events_series ON events(series_id, original_start);
```

- 实例是普通 `events` 行，复用现有列表/详情/冲突/提醒/RSVP。
- `original_start` 标识实例在系列中的原始时间；取消某次后保留该行（status cancelled），生成时跳过，避免“删了又被重建”。
- 系列元数据只存规则，不做运行时 RRULE 展开查询；创建/编辑时生成/更新实例。
- 这样避免所有读接口都引入 recurrence 展开逻辑，风险更低。

## 5. 替代方案

### A. 手动建多次（现状）

- 0 成本；改时间要逐条改；适合偶尔重复。

### B. 只存 RRULE，读取时展开

- 灵活、存储少；但所有列表/详情/冲突/提醒都要理解 RRULE，回归面大。
- **不推荐**课程项目。

### C. 系列表 + 实例行（本 CR 推荐）

- 读接口不变；实例复用现有能力；代价是写操作要生成/更新多行。
- 适合每周组会；最多 52 条/年，数据量可控。

### D. 只做“复制到下周”按钮

- 0.5–1 人日；不叫重复活动，但能解决一部分痛点。
- 适合先验证需求，不做系列模型。

### E. 完整“本次/本次及以后/整个系列”

- 5–7 人日以上；需要拆分系列、例外、批量冲突、提醒重排。
- **本期不做**；Phase 2 再评估。

## 6. 取舍

**如果做：**

- 5–7 人日 + 迁移；需要新表/新字段；
- 只做窄范围（weekly/biweekly、结束日期、整系列改、取消单次）；不做“本次及以后”；
- 批量冲突/提醒/DST 测试量大；
- 会与 CR-007（重新确认）、CR-006（找空闲）交互，需回归。

**如果不做：**

- 用户手动建多次；周会场景略麻烦；
- 省下时间给 CR-002/006/007 和 P0 稳定性；
- 可以先做替代方案 D（复制到下周）验证需求。

**建议：**

- **暂缓**；等 CR-002/006/007 完成、P0 稳定后再评估；
- 如果做，先做 Phase 1，不做“本次及以后”；
- 用系列表 + 实例行，避免 RRULE 读路径扩散。

## 9. 开放问题

1. 结束条件用日期还是次数？建议二选一，UI 默认日期。
2. 修改整个系列时，已开始的未来实例是否更新？建议只更新未开始的。
3. 取消某次后是否保留 cancelled 行？建议保留，防止重建。
4. 系列删除是否保留历史实例？建议保留历史，仅取消未来。
5. 是否需要“本次及以后”？Phase 2；本期不做。
6. 重复活动与 CR-007 重新确认如何交互？建议按实例重置。
7. 是否先做替代方案 D（复制到下周）验证需求？可以作为过渡。
