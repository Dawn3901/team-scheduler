## 1. 背景

用户不全是学生。个人日历是通用需求：课程、通勤、面试、兼职、个人事务都需要一个“只属于我”的日程层，只是学生用户对课表导入的需求更强烈。

当前产品只有团队级 `events`：

- `visibility=private` 可以隐藏标题/地点，但活动仍挂在某个团队下；
- 用户在多个团队时要重复创建；
- 退出团队后，个人数据随团队生命周期消失；
- 团队忙闲无法知道成员在团队之外的安排。

因此需要一个**用户级个人日历**：数据跟随用户，不跟随团队；团队只能看到“忙碌”，看不到内容。它也是后续 CR-003 外部课表导入的承载层。

**本 CR 只做个人日历本身，不做外部导入、不做个人任务、不做 AI 总结。**

---

## 2. 变更内容

### 2.1 目标

- 新增用户级 `personal_events`：跨团队、仅 owner 可见。
- 新增“我的日程”页面：个人事件 CRUD，按日期范围查看。
- 个人事件默认以“忙碌”参与团队忙闲，用户可逐条关闭 `share_busy`。
- 团队日历语义不变：仍是单团队单日历，不新增团队多日历。
- 外部课表/DDL 导入、个人提醒、个人任务不在本期。

### 2.2 本期范围

| 项 | 内容 |
|---|---|
| 数据 | 新表 `personal_events` + Alembic 迁移；不改现有 7 张表 |
| API | `GET /me/calendar`、`POST/PATCH/DELETE /me/events` |
| 权限 | 个人数据仅 owner 可见；他人访问 404；团队只看到忙碌块 |
| 忙闲 | `GET /teams/{team_id}/availability` 合并个人忙碌块，复用私密脱敏形状 |
| 前端 | 新增“我的日程”页面、个人事件编辑器；移动端 375px 可用 |
| 时区 | 存 UTC；全天/浮动时间按用户时区解释（`users.timezone`） |
| 测试 | CRUD 隔离、范围校验、全天/时区、share_busy、忙闲脱敏、P0 回归 |
| 文档 | docs/00 D2 说明、docs/02 新需求编号、docs/03 API/DDL、docs/ai/02 表清单、契约测试 |

### 2.3 明确不做（本期）

- **不做外部课表/ICS 导入**：拆到 [CR-003](CR-003-external-calendar-import.md) 单独评估。
- **不做 DDL / 乐学自动同步**：不保存学生密码、不服务端爬取；后续另立 CR。
- **不做个人任务**：个人 DDL 需要“个人任务”模型，和现有团队任务可见性冲突，单独评估。
- **不做个人事件提醒**：v1 不接提醒调度；避免与团队提醒、时区去重耦合。
- **不做双向日历同步**：不做 Google/Outlook/CalDAV。
- **不做多个个人日历**：一个用户一个个人日历，不引入 calendar 概念。
- **不做插件运行时 / AI 总结**：个人日历是核心功能，不是插件；AI 总结另立 CR/ADR。
- **不做离线写入**：保持服务器权威。

### 2.4 产品边界

- “个人日历”是**用户级忙碌层**，不是第二个团队日历；团队切换不改变个人数据。
- 团队日历仍是 D2 的“单团队单日历”；本 CR 需要一条 ADR 说明“个人日历不属于多团队日历”，并更新 docs/00 的 D2 备注。
- 个人事件默认 `share_busy=true`，队友只看到时间段与 `busy=true`，看不到标题/地点/描述；用户可关闭。
- 如果用户关闭 `share_busy`，团队忙闲里完全看不到该事件；这是隐私优先的取舍。

## 4. 替代方案

### A. 只做“我的日程”聚合视图（无新表）

- 在现有 `events`/`tasks` 上聚合“我组织的/我参与的/指派给我的”，提供个人视图。
- 优点：2–3 人日，无迁移，风险最低。
- 缺点：不是真正的个人日历；个人安排仍必须挂在某个团队下；多团队重复、退队丢失；无法承载外部导入。
- 适合：先验证“用户是否需要个人视图”，作为过渡。

### B. 个人事件继续用团队内私密活动

- 复用 `visibility=private` 的团队活动；队友只看到忙碌。
- 优点：零 schema，2–3 人日。
- 缺点：数据仍属于团队；多团队重复；退队丢失；个人日历没有独立生命周期。
- 适合：明确只服务单团队用户的临时方案。

### C. 用户级个人日历（本 CR 推荐）

- 新增 `personal_events`，跨团队、仅 owner 可见，忙闲合并。
- 优点：模型干净，符合“个人日历”预期；退队不丢个人数据；可承载后续导入。
- 缺点：7–9 人日、新表/迁移/API/UI/测试；需要产品决策。
- 适合：确认个人日历价值后，作为正式拓展。

### D. 改造 `events` 表，增加 nullable `team_id` / `scope`

- 用一张表同时存团队/个人事件。
- **拒绝**：所有团队查询、权限、序列化、索引都要改，回归面远大于新表；违反“小步可审”。

### E. 引入插件系统承载个人日历

- **拒绝**：个人日历是核心数据能力，不是可选插件；插件运行时还会带来第三方代码接触个人数据的风险。个人日历直接做成第一方模块。

## 5. 取舍

**如果做：**

- 需要 7–9 人日，必须从 P1 中砍掉一项（建议砍“评论”或“子任务”，保留重复活动/找空闲）；

- 演示增加“我的日程/个人忙碌”故事，但不挤占 P0 演示时间。

**如果不做：**

- 个人安排仍在团队日历外，AVAIL-6 的“找空闲”会漏掉个人事务；
- 产品保持纯团队定位，范围更稳；
- 可以先做替代方案 A（聚合视图）验证需求，再决定是否投入 C。

**建议：**

1. 先完成 `AVAIL-6 找空闲`，确认“忙闲 → 推荐时段”闭环；
2. 个人日历按 C 推进；外部课表导入等 CR-003 单独评估；
3. 如果排期不足，降级为 A，不硬上新表。

## 7. 方案细节（建议稿，批准后写入 docs/03）

### 7.1 数据模型

```sql
CREATE TABLE personal_events (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id INTEGER NOT NULL REFERENCES users(id),
    title TEXT NOT NULL,
    description TEXT,
    start_at DATETIME NOT NULL,
    end_at DATETIME NOT NULL,
    all_day INTEGER NOT NULL DEFAULT 0,
    location TEXT,
    color TEXT,
    share_busy INTEGER NOT NULL DEFAULT 1,
    created_at DATETIME NOT NULL,
    updated_at DATETIME NOT NULL,
    deleted_at DATETIME,
    CHECK (start_at < end_at)
);

CREATE INDEX ix_personal_events_user_start
    ON personal_events(user_id, start_at);
```

- 全部软删除，列表/详情默认过滤 `deleted_at IS NULL`。
- `share_busy=0` 时，不进入团队忙闲；详情仍仅 owner 可见。
- 不存 `visibility`：个人事件天然只对 owner 展示详情。
- 导入所需的 `source/external_uid/import_batch_id` 不在本表 v1 中；由 CR-003 通过新迁移补充，避免个人日历被导入需求绑死。

### 7.2 API 草案

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/me/calendar?from&to` | 个人事件范围查询；`from/to` 必填，跨度 ≤ 92 天 |
| POST | `/me/events` | 新建个人事件，201 |
| PATCH | `/me/events/{event_id}` | 编辑；仅 owner |
| DELETE | `/me/events/{event_id}` | 软删除，204 |

响应示例：

```json
{
  "id": 1,
  "title": "面试",
  "description": null,
  "start_at": "2026-11-04T01:00:00Z",
  "end_at": "2026-11-04T02:00:00Z",
  "all_day": false,
  "location": "线上",
  "color": "#2563EB",
  "share_busy": true,
  "updated_at": "2026-11-02T10:00:00Z"
}
```

### 7.3 权限与隐私

- 所有 `/me/*` 只允许当前用户；路径中不含 `user_id`，从 JWT 取。
- 他人无法通过猜 id 读取/修改/删除：统一 `404 NOT_FOUND`。
- `GET /teams/{team_id}/availability` 合并个人忙碌块时：
  - 只返回 `start_at/end_at/all_day/busy=true/visibility="private"/event_id=null/title=null`；
  - 不返回 `description/location/color`；
  - 只合并 `share_busy=1` 且未删除的个人事件；
  - 仅合并该团队成员的个人事件，不跨团队泄露。
- 个人事件标题/地点长度沿用现有文本规则；前端 React 转义，不拼 HTML。

### 7.4 前端

- 导航增加“我的日程”，路由建议 `/app/me/calendar`。
- 月/周视图可先只做列表 + 月视图；不引入第二个日历库。
- 个人事件编辑器：标题、时间、全天、地点、描述、颜色、`share_busy` 开关，并提示“队友只能看到忙碌，不显示标题”。
- 加载/空/错误/移动端状态与现有页面一致。
- 本期不显示“导入课表”入口；CR-003 批准后再加。

### 7.5 忙闲合并语义

- 团队忙闲 = 团队活动忙碌块 ∪ 成员个人 `share_busy` 忙碌块。
- 同一时间段重叠时保留多条 block（现有前端按 block 渲染）；不合并、不去重，避免丢失信息。
- 个人 block 的 `visibility` 复用 `"private"`，`event_id/title` 为 `null`；前端不需要新分支。
- `declined` 团队活动仍不计忙碌；个人事件无 RSVP。

## 10. 开放问题

1. 个人事件默认 `share_busy=true` 还是 `false`？建议默认 true（否则“找空闲”会漏个人安排），创建时明确提示。
2. “我的日程”是否要聚合团队成员活动/任务？建议 v1 只显示个人事件，v2 再加聚合，避免跨团队查询膨胀。
3. 个人事件是否需要提醒？建议 v1 不做；若用户强需求，v2 单独接调度。
4. 用户时区是否需要设置入口？`users.timezone` 已存在但未暴露；个人全天事件依赖它。
5. 多端同步：个人事件是否需要在 Web/Electron/Android 间实时刷新？v1 可以靠页面重取，v2 再评估 owner 级 WS。
6. 外部课表导入是否值得做？由 CR-003 评估；本 CR 只保证有承载表。
