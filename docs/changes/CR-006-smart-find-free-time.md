# CR-006 · 智能找空闲（AVAIL-6）

- 日期：2026-11-02
- 提出人：项目组讨论（AI 起草）
- 关联需求：`AVAIL-6`（P1，找空闲推荐）
- 依赖：[CR-002 个人日历](CR-002-personal-calendar.md)（可选：个人忙碌块）
- 类型：范围 / 接口 / 算法
- 优先级：P1（高价值，建议优先实施）
- 状态：**已批准（A/B 两人，2026-11-02）；已排期 W3（2026-11-16–11-19）**

---

## 1. 背景

现有 `GET /teams/{team_id}/availability` 只返回每个成员的忙碌块，用户仍要自己盯着时间轴找共同空档。团队规模稍大、时间跨度稍长时，这件事很费劲。

`AVAIL-6` 已列入 P1：给定时长/成员/日期范围，直接返回前 3 个可用时段。它复用现有忙闲数据，不需要新表，是当前性价比最高的拓展。

---

## 2. 变更内容

### 2.1 目标

- 新增“找空闲”入口：选择成员、时长、日期范围，返回前 3 个候选会议时段。
- 区分**必到成员**与**可选成员**：必到成员必须全部空闲；可选成员按可参加比例评分。
- 默认工作时间 09:00–18:00（团队时区），支持查询参数覆盖；不需要新表。
- 私密活动/个人事件只作为忙碌块参与，不泄露标题。
- 不自动创建活动；用户选定候选后再走现有创建流程。

### 2.2 本期范围

| 项 | 内容 |
|---|---|
| API | `GET /teams/{team_id}/availability/suggestions` |
| 算法 | 忙闲区间合并 → 必到成员求交 → 工作时间过滤 → 候选评分 → Top 3 |
| 成员 | `member_ids` 参与范围；`required_ids` 必到子集；未传则全部必到 |
| 工作时间 | 查询参数 `work_start/work_end`，默认 09:00–18:00；团队时区 |
| 隐私 | 只使用 busy 时间段；不返回标题/地点/描述 |
| 前端 | 忙闲视图/日历增加“找空闲”面板，展示候选与可参加成员 |
| 测试 | 区间合并、交集、全天、DST、私密、declined、必到/可选、无候选 |
| 文档 | docs/03 §5、docs/ai/02、契约测试 |

### 2.3 明确不做

- **不自动创建活动**：只返回候选；创建仍走现有活动表单/接口。
- **不做跨团队找空闲**：一次只针对一个团队。
- **不做日历双向同步**：只读忙闲。
- **不做 AI 推荐**：评分是确定性规则，不接 LLM。
- **不做长期偏好学习**：如“不喜欢周一上午”，后续再评估。
- **不做新表**：工作时间等参数先走 query/default，不做团队设置表。

## 3. API 草案

### GET `/teams/{team_id}/availability/suggestions`

查询参数：

| 参数 | 必填 | 说明 |
|---|---|---|
| `from` / `to` | 是 | 带时区；跨度 ≤ 31 天 |
| `duration_minutes` | 是 | 15–480 |
| `member_ids` | 否 | 逗号分隔；默认团队全部活跃成员 |
| `required_ids` | 否 | 必到子集；默认等于 `member_ids` |
| `work_start` / `work_end` | 否 | `HH:MM`，默认 `09:00`/`18:00` |
| `buffer_minutes` | 否 | 候选前后缓冲，默认 0，最大 60 |
| `include_weekend` | 否 | 默认 false |

响应：

```json
{
  "from": "2026-11-03T00:00:00Z",
  "to": "2026-11-10T00:00:00Z",
  "duration_minutes": 60,
  "working_hours": { "start": "09:00", "end": "18:00", "timezone": "Asia/Shanghai" },
  "suggestions": [
    {
      "start_at": "2026-11-04T06:00:00Z",
      "end_at": "2026-11-04T07:00:00Z",
      "score": 0.92,
      "required_free": true,
      "available_member_ids": [1, 2, 3],
      "missing_optional_ids": [4],
      "reasons": ["必到成员全部空闲", "3/4 成员可参加"]
    }
  ]
}
```

- 最多返回 3 条；没有候选时返回空数组，不报错。
- 候选按评分降序，同分按开始时间升序。
- 私密/个人忙碌块只影响可用性，不出现在响应明细里。

## 4. 算法

```text
1. 校验 from/to、duration、成员属于团队且 active。
2. 取团队活动 + 成员个人 busy（若 CR-002 已实现）：
   - 只取 confirmed、未删除；
   - declined 参与者不计 busy；
   - 私密活动只保留时间段。
3. 每个成员合并重叠 busy 区间。
4. 在 [from,to] 内按工作时间切出候选窗口（可跨天，但每个候选必须完整落在同一天的工作时间内）。
5. 对必到成员求交集；交集内的连续空档 ≥ duration + 2*buffer 才保留。
6. 可选成员按“可参加比例”加权；评分建议：
   score = 0.7 * required_coverage + 0.3 * optional_coverage
   required_coverage 恒为 1（硬约束），optional_coverage = 可参加可选人数 / 可选总人数。
7. 取 score 最高的 3 个；同分按时间升序。
```

- 工作时间按团队时区解释，再转 UTC 输出。
- 全天活动视为整天 busy。
- 周末默认排除；`include_weekend=true` 时纳入。
- 跨 DST 的日期按团队时区计算，禁止用固定 24h 偏移。

## 6. 替代方案

### A. 只展示忙闲，不推荐（现状）

- 零成本；用户自己找。适合小团队/短时间，但体验一般。

### B. 只做必到成员交集，不做可选成员评分

- 2 人日；算法简单、结果确定。
- 缺点：可选成员只能事后看；适合 MVP 第一阶段。

### C. 必到 + 可选加权 Top 3（本 CR 推荐）

- 3–4 人日；结果更实用；评分规则要写清并测试。

### D. AI 推荐/自然语言找时间

- 需要 LLM、成本和隐私评审；**不在本期**。确定性算法已足够。

### E. 跨团队/多日历找空闲

- 需要用户级忙闲聚合与多团队权限；**拒绝**，超出本期。

## 7. 取舍

**如果做：**

- 3–4 人日，无迁移，复用现有 availability；
- 直接强化产品差异化；和 CR-002/CR-003 组合成学生团队故事；
- 需要明确工作时间/周末/缓冲等默认值，避免“推荐了但用户不接受”。

**如果不做：**

- 忙闲仍可用，只是用户要自己找；
- 省下时间给 CR-002 或测试；但失去一个高性价比亮点。

**建议：**

- 先做 MVP：必到成员 + 工作时间 + Top 3；可选成员评分可放第二阶段；
- 依赖 CR-002 时，个人忙碌块自动参与；未实现则只算团队活动；
- 默认不自动创建，候选卡片点“创建活动”再走现有表单。

## 10. 开放问题

1. 默认工作时间 09:00–18:00 是否合适？是否需要按团队配置？
2. 是否默认排除周末？午休 12:00–13:00 是否要排除？
3. 可选成员评分权重 0.7/0.3 是否合理？是否需要“至少 N 人可参加”的硬约束？
4. 候选是否允许跨天/跨工作时间？建议只允许完整落在同一天工作时间内。
5. 是否需要“推荐后一键创建活动”？建议先只跳转创建表单，不自动创建。
6. 个人日历未实现时，是否先只按团队活动找空闲？建议是。
