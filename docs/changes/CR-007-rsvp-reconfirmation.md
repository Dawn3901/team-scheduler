# CR-007 · 活动变更重新确认（RSVP-6）

- 日期：2026-11-02
- 提出人：项目组讨论（AI 起草）
- 关联需求：`RSVP-6`（P1，组织者修改时间后要求参与者重新确认）
- 类型：范围 / 接口 / 交互
- 优先级：P1（建议在 CR-006 之后）
- 状态：**已由 CR-009 实施（PR #23，2026-11-11），待验收**（原：已批准/已排期 W3）

---

## 1. 背景

现有规则：组织者修改时间/地点后，系统给参与者发 `event.updated` 通知，但参与者原来的 RSVP 仍是 `accepted`。这会导致：

- 组织者以为大家都看到变更并仍然参加；
- 参与者没注意到时间变了，按旧时间赴约；
- 组织者无法区分“已确认新时间”和“只是没重新点”。

`RSVP-6` 要求变更后重新确认。本 CR 补这个状态机，不改活动创建/删除/冲突逻辑。

---

## 2. 变更内容

### 2.1 目标

- 组织者修改活动的**时间或地点**后，非组织者参与者需要重新确认。
- 已接受/待定的参与者状态回到 `pending`，`responded_at` 清空，并收到一次通知。
- 组织者保持 `accepted`；已拒绝的参与者保持 `declined`（不强制重新确认）。
- 活动取消、已结束、未实际变更时不触发。
- v1 不新增字段，复用现有 `event_participants.response/responded_at`。

### 2.2 触发条件

同时满足：

- 请求是 `PATCH /events/{event_id}`；
- 实际修改了 `start_at`、`end_at` 或 `location`（值真的变化，不是原值回传）；
- 活动未取消、未结束；
- 操作者是组织者/Admin。

不触发：

- 只改标题/描述/颜色/可见性；
- 活动取消（`status=cancelled`）；
- 活动已开始/结束（现有规则本来就不允许改时间/地点）；
- 冲突强制保存但没有实际时间/地点变化。

### 2.3 状态变化

| 参与者 | 变更前 | 变更后 |
|---|---|---|
| 组织者 | accepted | accepted（不变） |
| 非组织者 | accepted / tentative | pending，`responded_at=null` |
| 非组织者 | declined | declined（不变） |
| 非组织者 | pending | pending（不重复通知） |
| 被移除者（declined 且无 responded_at） | declined | declined（不可见，不通知） |

> 推荐保留 declined：他们已经明确拒绝，时间变化不应强迫重新表态；如果产品希望“所有人重新确认”，在评审时改成全部非组织者重置。

### 2.4 通知

- 对“从 accepted/tentative 变为 pending”的人发一次通知：
  - `type="event.updated"`（复用现有类型，不新增 WS 消息类型）；
  - 标题/正文说明“活动时间/地点已变更，请重新确认”；
  - payload 带 `team_id/event_id`。
- 已经是 pending 的人不重复通知；同一参与者一次变更只通知一次。
- 通过现有 WS `calendar.changed` 刷新，不新增消息类型。

### 2.5 明确不做

- **不做“每次变更保留历史回应版本”**：v1 用重置，简单可验证；保留历史另立 CR。
- **不做“部分参与者重新确认”**：v1 统一按状态重置。
- **不做重复活动实例的重新确认**：重复活动本身是 CR-008；届时再适配。
- **不改 RSVP 接口路径/状态枚举**：仍是 accepted/declined/tentative/pending。
- **不做邮件/推送**：站内通知 + WS 即可。

## 4. 替代方案

### A. 重置 accepted/tentative 为 pending（本 CR 推荐）

- 无 schema；复用现有状态；实现简单；测试明确。
- 缺点：丢失“旧时间曾接受”的历史；用户可能不记得自己改过。

### B. 增加 `event_version` / `confirmation_version`

- 保留旧回应，标记“需重新确认”；语义更好。
- 缺点：迁移、前端状态、通知去重更复杂；3–5 人日。
- 适合：后续需要审计/历史时再做。

### C. 只发通知，不重置状态

- 0.5 人日；但组织者仍无法区分是否确认；不满足 RSVP-6。

### D. 所有非组织者（含 declined）全部重置

- 简单，但强迫已拒绝者重新表态；不推荐。

### E. 只对 accepted 重置，tentative 保持

- 更保守，但“待定”同样没确认新时间；建议 accepted + tentative 都重置。

---

## 5. 取舍

**如果做：**

- 2–3 人日，无迁移；补上一个真实的协作漏洞；
- 需要接受“旧回应不保留”的取舍；
- 通知要避免重复，测试并发 PATCH；
- 与 CR-008 重复活动有交互，届时需要按实例处理。

**如果不做：**

- 参与者可能按旧时间赴约；组织者误以为已确认；
- 省下 2–3 人日，但 RSVP 闭环不完整。

**建议：**

- 批准方案 A；在 UI 明确提示“时间已变更，请重新确认”；
- 如果后续需要审计，再升级到方案 B。

## 7. 实现要点

### 7.1 服务层

`patch_event` 中：

1. 计算 `changed_time_or_location`（用旧值与新值比较，排除原值回传）。
2. 保存活动字段。
3. 若触发：
   - 遍历参与者；
   - 跳过组织者、已 declined、被移除者；
   - 对 accepted/tentative：`response="pending"`、`responded_at=None`；
   - 对状态实际变化的人发一次 `event.updated` 通知；
   - 已是 pending 的人不发通知。
4. 同一事务提交；失败回滚，避免活动改了但参与者没重置。

### 7.2 通知去重

- 只对“状态发生变化”的人发通知，天然去重；
- 同一活动连续两次 PATCH：第一次重置并通知；第二次已是 pending，不再通知；
- 不新增 dedupe key，不依赖时间戳。

### 7.3 前端

- 参与者列表：`response=pending` 显示“待重新确认”；
- 当前用户 `my_response=pending` 时，RSVP 按钮高亮/提示；
- 活动详情显示“组织者已修改时间/地点”；
- 复用现有 WS `calendar.changed` 刷新，不新增消息类型。

## 8. 验收标准

- [ ] 组织者修改时间后，accepted/tentative → pending，`responded_at=null`。
- [ ] 组织者保持 accepted；declined 保持 declined；pending 不重复通知。
- [ ] 只改标题/描述/颜色/可见性不触发重置。
- [ ] 活动取消/已结束不触发重置。
- [ ] 参与者不能通过 PATCH 活动触发（仍 403）。
- [ ] 同一变更每人最多收到一条通知；连续 PATCH 不重复轰炸。
- [ ] 并发 PATCH 后状态一致，不出现“活动已改但参与者未重置”。
- [ ] 前端显示“待重新确认”，RSVP 可重新提交。
- [ ] P0 全量回归通过；docs/03 §5.4 更新。

## 9. 开放问题

1. declined 是否也要重新确认？建议不；如果产品要求“所有人都确认”，改为全部非组织者重置。
2. 只改地点是否触发？建议触发（地点影响是否到场）；如果只改线上链接，可另议。
3. 是否需要保留旧回应历史？v1 不保留；需要审计时升级到方案 B。
4. 重复活动实例如何重新确认？CR-008 批准后按实例处理。
5. 通知文案/类型是否复用 `event.updated`？建议复用，避免新增 WS 类型。
