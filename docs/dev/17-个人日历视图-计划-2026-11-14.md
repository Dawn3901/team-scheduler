## 1. 目标

把「我的日程」从“按天列表”改造成**基本复刻团队日历**的个人日历：

1. 保留 **月视图**与 **周视图**，交互、样式与团队日历一致；
2. **不提供单日视图**；团队日历里“单日=成员分栏”的位置，换成 **任务清单**；
3. 视图切换为：**月 / 周 / 任务清单**（三个选项）；
4. 日历里**只出现“我的日程 + 我的任务 + 我参加/待回应的团队活动”**；不需要我参加的团队活动不显示（本来也不返回）；
5. 个人日历只区分三种状态：**红=紧急（任务逾期/24h 内、个人事件 2h 内）、蓝=活动待回应、绿=其余**。

## 4. 数据与接口

### 4.1 决策：新增只读聚合端点 `/me/agenda`

用户已选择“新增 `/me/agenda`”。理由：切视图/翻页时只发 1 个请求，周/月切换更快，也避免三个查询各自 30/92 天限制不一致。

### 4.2 接口契约（CR-013）

```http
GET /api/v1/me/agenda?from=<ISO>&to=<ISO>
```

- `from/to`：必填、带时区、跨度 ≤ **92 天**（与 `/me/calendar` 一致，复用 `validate_range`）；
- 返回：

```json
{
  "from": "2026-11-09T00:00:00Z",
  "to": "2026-11-16T00:00:00Z",
  "events": [
    {
      "id": "p:12",
      "kind": "personal",
      "title": "宿舍",
      "start_at": "2026-11-13T05:00:00Z",
      "end_at": "2026-11-13T06:00:00Z",
      "all_day": false,
      "location": "宿舍",
      "team_id": null, "team_name": null,
      "my_response": null, "needs_confirmation": false,
      "status": null
    },
    {
      "id": "t:31",
      "kind": "team_event",
      "title": "周会",
      "start_at": "2026-11-12T01:00:00Z",
      "end_at": "2026-11-12T02:00:00Z",
      "all_day": false,
      "location": null,
      "team_id": 2, "team_name": "软工大作业",
      "my_response": "accepted", "needs_confirmation": false,
      "status": "confirmed"
    }
  ],
  "tasks": [
    {
      "id": 41, "team_id": 3, "team_name": "软工大作业",
      "title": "补交实验报告", "status": "todo", "priority": "high",
      "due_at": "2026-11-01T02:00:00Z", "overdue": true
    }
  ]
}
```

- `events` 合并两类：个人事件 + 我在各团队中 `accepted/tentative/pending` 的团队活动；`declined`、未邀请、被移除邀请、已取消/已删除都不返回；
- `tasks`：与我 `/me/tasks` 相同口径（指派给我、未完成、逾期或 30 天内）；
- 契约影响：HTTP 操作 **41 → 42**，需同步 `docs/03` 契约表与 `test_api_contract.py`；
- 实现：新增 `services/agenda.py` 组装 `personal.list_range` + `team_feed.my_team_events` + `my_tasks`，**不新增表、不改现有端点**。

### 4.3 紧急度与颜色（唯一颜色维度）

| 颜色 | 条件 |
|---|---|
| **红（紧急）** | 任务：逾期或 24 小时内截止；个人事件：进行中或 2 小时内开始 |
| **蓝（待回应）** | 团队活动 `my_response = pending`（含待重新确认） |
| **绿（正常）** | 其余：我参加的活动、未来的个人事件、3 天外的任务；已完成任务用浅灰/无边框 |

- 阈值写成前端常量，单测覆盖边界；
- **颜色不是唯一信息**：任务保留“已逾期 / 24 小时内”文字；待回应活动保留“待回应”标记（无障碍要求）。

## 5. 技术设计

### 5.1 统一条目模型

```ts
// apps/web/src/lib/personalItems.ts
export type PersonalItemKind = "personal_event" | "team_event" | "task";
/** 红=紧急、蓝=活动待回应、绿=正常；已完成=done（浅灰）。 */
export type PersonalUrgency = "urgent" | "pending" | "normal" | "done";

export interface PersonalItem {
  id: string;                      // "e12" | "t34" | "p56"
  kind: PersonalItemKind;
  title: string;
  start: Date;                     // 团队/用户时区下的墙上时间（与团队日历一致）
  end: Date;
  allDay: boolean;
  urgency: PersonalUrgency;
  subtitle?: string;               // "软工大作业 · 待回应"
  href?: string;                   // 团队活动/任务跳转
  original: PersonalEvent | MyTeamEvent | MyTask;
}
```

- 纯函数 `toItems(agenda, zone, now)`，输入即 `/me/agenda` 的响应，Vitest 单测；
- `urgencyOf(item, now)` 单独实现，阈值常量集中定义（24h / 2h / 3 天）；
- 颜色常量：红 `#dc2626`、蓝 `#2563eb`、绿 `#16a34a`、完成灰 `#94a3b8`。

### 5.2 组件与复用策略

| 组件 | 处置 |
|---|---|
| `CalendarTimeline` | **直接复用**（已支持 `items`/`backgroundItems`/`columns`/`onSelect`/`onCreate`） |
| 月视图 | 直接复用 `react-big-calendar` + 现有 `localizer`；`eventPropGetter` 按 urgency 着色（红/蓝/绿） |
| 视图切换 | 抽出 `ViewSwitcher`（月/周/任务清单），团队日历仍用月/周/日，**组件支持自定义视图集合** |
| 页面 | 新建 `PersonalCalendarPage` 替换现有 `MyCalendarPage` 的渲染层；保留下方任务清单作为视图之一 |
| 公共样式 | 复用 `.rbc-*`、`.timeline-*` 与日历卡片框架，新增 `.personal-calendar-*` 少量样式 |

> 原则：**不复制团队日历的样式**，能复用就复用；团队日历不接受任何行为变化。

## 13. §4.4 `share_busy` 开关的处理

用户问题：“个人日历为什么还要保留‘参与团队忙闲’开关？应该没必要。”

结论：**从个人事件编辑弹窗移除**。理由：

- 个人事件默认就应该作为“忙碌”参与团队忙闲，这是 CR-002 的设计意图（否则“找空闲”会漏个人安排）；
- 让用户逐条关掉，反而制造“我以为会被看到、其实没看到”的误解；
- 开关放在个人日历里，语义也不直观（用户看不到团队忙闲视图）。

处理方式：

- 前端移除开关，**默认 `share_busy=true`**；
- 后端字段保留（数据库/契约不变），旧数据中 `share_busy=false` 的事件继续按原值生效，不做迁移；
- 若未来需要“隐私模式”，另立 CR 做成用户级设置，而不是逐条开关。
