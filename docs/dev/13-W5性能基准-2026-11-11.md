# W5-04 性能基准（2026-11-11）

> 脚本：[`scripts/bench.py`](../../scripts/bench.py)。数据写入独立 `debug/bench/bench.db`，不读写 `server/data/teamsync.db`。

## 数据集

- 50 个用户，1 个团队，50 名成员。
- 10,000 场活动，每场 3 名参与者（约 30,000 条参与者行）。
- 5,000 个任务。
- 时间跨度 2026-11-01 起约一年；查询基准窗口为 31 天/7 天。

## 复现

```powershell
cd E:\My_Files\SomethingInteresting\team-scheduler
server/.venv/Scripts/python.exe scripts/bench.py --reset
```

Linux/WSL 用 `server/.venv/bin/python scripts/bench.py --reset`。

输出：`debug/bench/report.json`（本地，gitignore）。

## 结果（Windows Python 3.13 venv，单机 TestClient 串行）

| 查询 | 中位耗时 | 最小 | 最大 | 响应字节 | 返回量 |
|---|---:|---:|---:|---:|---:|
| `GET /teams/1/events`（31 天） | **108.57 ms** | 106.21 | 119.09 | 74,210 | 849 |
| `GET /teams/1/availability`（7 天，50 人） | **2,853.18 ms** | 2,789.32 | 2,868.59 | 94,563 | 50 人 |
| `GET /teams/1/tasks?limit=100` | **83.50 ms** | 74.19 | 135.43 | 35,910 | 5,000 total |

造数耗时约 **1.85 s**。

## 结论与风险

- 31 天活动查询和任务首页对 2 人演示规模足够；**7 天 50 人忙闲查询约 3 秒**，是当前最明显的性能瓶颈。
- 忙闲接口一次返回全部成员块，未分页/缓存；50 人已是产品加入上限，演示 3–20 人时压力更小，但不应宣称“万级活动下仍流畅”。
- 这是单机串行 TestClient 观测，包含路由、鉴权、序列化与 SQLite，**不是网络延迟、并发吞吐或 p95**。
- 未在本次改查询算法；若 W5 后仍有时间，优先做忙闲分页/按需成员、缓存或 SQL 聚合，而不是加 P1 功能。

## 证据边界

- 只测了 3 个只读接口；未测写接口、WebSocket 广播、导出、并发。
- `debug/bench/report.json` 是本地产物，不入库；本文记录本次观测值。
