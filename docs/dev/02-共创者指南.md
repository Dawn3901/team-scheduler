# 共创者指南：从零搭建开发环境

> 读者：第一次参与 TeamSync、准备在本机跑起来并提交第一个改动的同学。  
> 目标：按本文从一台干净电脑开始，完成安装 → 配置 → 迁移 → 启动 → 跑测试 → 提交第一个 PR。  
> 已经能跑、只想改代码的，直接看 [开发者指南](01-开发者指南.md)。

## 0. 先了解三件事

1. **项目组是 2 人 + AI**。AI 可以写实现/测试/文档草稿，但不能做需求决策、契约批准、安全签字和最终验收；每个 PR 至少另一名人类 review，认证/权限/私密/时区/迁移/冲突/提醒这些关键路径两人都要看。
2. **需求与契约是权威**。写代码前先读 [需求规格](../02-需求规格说明书.md) 与 [接口契约](../ai/02-接口与数据契约.md)；不要因为“这样更方便”改字段、状态码或表结构。
3. **能跑起来才算开始**。本文每一步都给了验证命令；报错先看 [第 11 节常见故障](#11-常见故障)，不要靠猜。

> **仓库当前状态（2026-10-28）**：本地工作区还没有第一个 git 提交。首次 clone/push 前，需要维护者先完成初始提交；否则新成员无法获取代码。见 [代码审查报告 R-01](03-代码审查报告-2026-10-28.md)。

## 1. 你需要什么

### 1.1 必备工具

| 工具 | 版本 | 用途 | 检查命令 |
|---|---|---|---|
| Git | 2.30+ | 版本管理 | `git --version` |
| Python | **3.12+**（推荐 3.12 / 3.13） | 后端 | `python --version` |
| Node.js | **22 LTS** | 前端/工具链 | `node -v` |
| pnpm | **12.11.2**（与 CI 一致） | 包管理 | `pnpm -v` |
| GNU Make | 4.x（可选） | 统一命令入口 | `make --version` |

> 本机验证过的组合：Windows Python 3.13.5 + Node 22.19.0 + pnpm 12.11.2；CI 用 Python 3.12 + Node 22 + pnpm 12.11.2。  
> Python 3.14 尚未在 CI 覆盖，建议用 3.12/3.13，避免把“本机能跑”当成“团队能跑”。

### 1.2 可选工具

- `sqlite3` 命令行：查看本地数据库（没有也能用 Python 查）。
- Android Studio / JDK 17：W4 之后做 Android 壳时需要。
- Windows 10/11：做 Electron 托盘与系统通知时需要。
- VS Code 插件：Python、Ruff、ESLint。

### 1.3 关于 Make

`make` 只是命令封装，不是硬依赖。Makefile 里用了 POSIX shell 语法（`[ -d ... ]`、`||`）和 GNU Make 的 `ifeq`：

- **Windows**：需要 GNU Make + 可用的 `sh.exe`（Git for Windows 的 `bin` 在 PATH 里）。如果 `make setup` 报 `'[' 不是内部或外部命令`，说明 recipe 走的是 cmd，请改用 [1.5 手动安装](#15-手动安装没有-make-时)，或把 Git 的 `bin` 加到 PATH。
- **macOS**：系统自带的 `/usr/bin/make` 是 BSD make，不认 `ifeq`。用 `brew install make` 后执行 `gmake`，或直接用手动命令。
- **Linux / WSL**：`sudo apt install build-essential` 即可。

## 2. 安装工具链

### 2.1 Windows 10/11

在 **PowerShell** 中（建议以普通用户执行，必要时再开管理员）：

```powershell
winget install --id Git.Git -e
winget install --id Python.Python.3.12 -e
winget install --id OpenJS.NodeJS.LTS -e
```

安装 GNU Make（三选一，能装哪个用哪个）：

```powershell
choco install make        # 需要 Chocolatey
scoop install make        # 需要 Scoop
# 或安装 MSYS2，使用其中的 make
```

启用 pnpm（Node 22 自带 Corepack）：

```powershell
corepack enable
corepack prepare pnpm@12.11.2 --activate
pnpm -v
```

如果 `corepack` 不可用或权限不足：

```powershell
npm install -g pnpm@12.11.2
```

验证：

```powershell
git --version
python --version        # 应为 3.12+
node -v                 # 应为 v22.x
pnpm -v                 # 应为 12.x
make --version          # 可选
```

> 如果 `python` 指向 Microsoft Store 的占位程序，用 `py -3.12 --version` 检查，并在 `make setup` 时传 `PYTHON="py -3.12"`，或按 1.5 手动建 venv。

### 2.2 WSL / Ubuntu

```bash
sudo apt update
sudo apt install -y build-essential git python3.12 python3.12-venv curl
```

> 如果发行版仓库没有 `python3.12`，用 deadsnakes PPA 或 pyenv 安装 3.12/3.13；不要用 3.10/3.11 硬跑，`pyproject.toml` 要求 ≥3.12。

Node 22 建议用 nvm 安装（按 nvm 官方 README 安装脚本，然后）：

```bash
nvm install 22
nvm use 22
node -v
corepack enable
corepack prepare pnpm@12.11.2 --activate
pnpm -v
```

> **强烈建议把仓库放在 Linux 文件系统**（例如 `~/projects/team-scheduler`），不要放在 `/mnt/c`、`/mnt/e`。跨文件系统会让 `pnpm install`、文件监听和 SQLite 明显变慢，并可能遇到锁/原生模块问题。  
> 如果必须在 `/mnt/e` 下开发（当前仓库就在这里），请**只在一个平台上装依赖**：Windows 装的 `node_modules` 里有 Windows 原生二进制，WSL 里构建会报 `Cannot find module '../rolldown-binding.linux-x64-gnu.node'`。

### 2.3 macOS

```bash
xcode-select --install          # 提供 git / 编译工具
brew install python@3.12 make
# Node 22：从 nodejs.org 安装 LTS 安装包，或用 nvm 安装；
# `brew install node` 可能装到更高版本，不保证是 22
node -v                          # 确认是 v22.x
```

`brew install make` 安装的是 GNU make，可执行文件通常叫 `gmake`：

```bash
gmake --version
corepack enable
corepack prepare pnpm@12.11.2 --activate
```

之后把本文的 `make` 换成 `gmake`，或直接用手动命令。

## 3. 获取代码并建分支

```bash
git clone <课程仓库地址> team-scheduler
cd team-scheduler
git status
```

第一个改动不要直接在 `main` 上做：

```bash
git switch main

# git switch -c docs/dev-guide       # 文档
```

分支命名用 `feat/`、`fix/`、`docs/`、`test/`、`chore/` 前缀；一个分支只做一件事。

## 4. 配置 `.env`

`.env` 在**仓库根目录**（不是 `server/.env`），已被 gitignore；模板是 `.env.example`。

```bash
cp .env.example .env
```

PowerShell：

```powershell
Copy-Item .env.example .env
```

生成随机 `SECRET_KEY`：

```bash
# Linux / WSL / macOS
python3 -c 'import secrets; print(secrets.token_urlsafe(48))'
```

```powershell
# Windows PowerShell
python -c "import secrets; print(secrets.token_urlsafe(48))"
```

把输出粘贴到 `.env` 的 `SECRET_KEY=` 后面。**不要**把 `.env` 提交，也不要把真实密钥贴进 issue/聊天记录。

最小配置示例（其余保持默认即可）：

```dotenv
SECRET_KEY=<你生成的随机值>
DATABASE_URL=sqlite:///./data/teamsync.db
CORS_ORIGINS=http://localhost:5173
TEAM_TIMEZONE=Asia/Shanghai
ACCESS_TOKEN_EXPIRE_DAYS=7
LOG_LEVEL=INFO
```

说明：

- `DATABASE_URL` 的相对 SQLite 路径会由 `resolve_database_url()` 固定解析到 `server/`，与启动目录无关；默认库是 `server/data/teamsync.db`。
- 缺 `SECRET_KEY` 时，导入配置立即报 Pydantic `Field required`；先检查 `.env` 是否在仓库根目录、文件名是否就是 `.env`。

## 5. 安装依赖

### 5.1 用 make（推荐，Git Bash / WSL / Linux / macOS + GNU make）

```bash
make setup
```

它会：

1. 检查 Python ≥ 3.12；
2. 检查 `server/.venv` 是否属于另一个平台；
3. 在 `server/` 建 venv 并 `pip install -e ".[dev]"`；
4. 在仓库根目录 `pnpm install`。

如果系统里有多个 Python：

```bash
make setup PYTHON="py -3.12"        # Windows
make setup PYTHON=/usr/bin/python3.12
```

### 5.2 手动安装（没有 make，或 make 不可用）

**Windows PowerShell：**

```powershell
cd server
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"
cd ..
pnpm install
```

**Linux / WSL / macOS：**

```bash
cd server
python3.12 -m venv .venv
.venv/bin/python -m pip install --upgrade pip
.venv/bin/python -m pip install -e ".[dev]"
cd ..
pnpm install
```

### 5.3 跨平台注意

- `.venv` 不能跨平台复用：从 Windows 切到 WSL（或反向）先删 `server/.venv`，再重新安装。
- `node_modules` 也带平台原生二进制（例如 Vite 8 的 rolldown）：切换平台时删除根目录及各 workspace 的 `node_modules`，重新 `pnpm install`。
- 不要在 WSL 里对 Windows 侧的 `node_modules` 跑 `pnpm install`；反过来也一样。

## 6. 初始化数据库

```bash
make migrate
```

或手动：

```bash
cd server
.venv/bin/python -m alembic upgrade head          # Windows: .venv\Scripts\python.exe -m alembic upgrade head
```

预期输出包含：

```text
Running upgrade  -> 0001_initial
```

验证：

```bash
.venv/bin/python -m alembic current
# 0001_initial (head)
```

数据库文件在 `server/data/teamsync.db`（以及 `-wal` / `-shm`）。需要重置开发库时，先停后端，再删这三个文件并重新 `make migrate`。

> Windows 控制台里迁移日志的中文可能是乱码，这是代码页问题，不影响迁移结果。执行 `chcp 65001` 或设置 `$env:PYTHONUTF8=1` 可正常显示。

## 7. 启动

推荐两个终端，日志更清楚。

**终端 A：后端**

```bash
make dev-api
# 或 cd server && .venv/bin/python -m uvicorn app.main:app --reload --port 8000
```

**终端 B：前端**

```bash
make dev-web
# 或 pnpm --filter @teamsync/web dev
```

也可以用 `make dev` 同时启动（内部是 `make -j2`，日志会交错）。

验证：

1. 浏览器打开 <http://localhost:5173>，页面应显示“后端 已连接”，并显示 `db: ok`。
2. 命令行：

```bash
curl http://127.0.0.1:8000/health
# {"status":"ok","db":"ok"}
```

3. 打开 <http://127.0.0.1:8000/docs> 能看到 OpenAPI 文档。

停止：在对应终端按 `Ctrl+C`。如果端口被残留进程占用：

```bash
# Linux / WSL / macOS
lsof -i :8000
lsof -i :5173

# Windows
netstat -ano | findstr :8000
taskkill /PID <PID> /F
```

## 9. 第一次贡献：走一遍完整流程

下面以“W1-04 建 users / teams / team_members 迁移”为例，其他任务同理。

### 9.1 选任务、读文档

1. 在 [六周项目计划](../01-六周项目计划.md) 找到本周任务（W1-04 起）。
2. 在 [需求规格](../02-需求规格说明书.md) 找到对应需求编号（AUTH、TEAM）。
3. 在 [概要设计](../03-概要设计说明书.md) 找到表结构与接口。
4. 读 [接口与数据契约](../ai/02-接口与数据契约.md) 和 [变更控制](../ai/04-变更控制与追踪.md)。要加字段/改状态码，先写 CR。
5. 读 [AGENTS.md](../../AGENTS.md) 的 DoD、改动边界、评审清单。

### 9.2 建分支、写测试

```bash
git switch -c feat/db-users-teams
```

先写会失败的测试（例如用户名唯一、跨团队 404、密码不进响应），再实现。不要先写一大堆代码再补“能过”的测试。

### 9.3 实现、迁移、接前端

- 业务规则放 `server/app/services/`；router 只做参数校验与依赖注入。
- 新表用 Alembic，不手改数据库；生成后逐行 review。
- 共享类型/请求函数放 `packages/shared`，不要在页面里重复定义。
- 需要改 API/表/错误码时，同步 `docs/03` 与 `docs/ai/02`，并留 CR 记录。

### 9.4 自测

```bash
make check
# 涉及迁移时
make migrate
# 涉及页面/构建时
pnpm --filter @teamsync/web build
```

再手工走一遍主流程与边界：无权限、跨团队、私密活动、23:30/00:00、全天、空状态、错误提示。

### 9.5 提交

```bash
git status
git diff --stat
git diff
git add <具体文件>
git commit -m "feat(db): 新增 users/teams/team_members 迁移 (AUTH-1, TEAM-1)"
```

提交前自查：

- [ ] 没有 `.env`、密钥、token、调试日志、`console.log`、`print`。
- [ ] 没有顺手重构/格式化整个文件。
- [ ] 新逻辑有测试；修 bug 有复现用例。
- [ ] 文档同步（API/表/命令）。
- [ ] diff 能在 5 分钟内被看懂。

### 9.6 推送、开 PR、评审

```bash
git push -u origin feat/db-users-teams
```

PR 描述建议：

```markdown
## 关联需求
AUTH-1 / TEAM-1

## 改了什么
- 新增 3 张表与迁移
- 补充唯一约束与软删除列
- 加契约测试

## 怎么验证
- [x] `make check`
- [x] `alembic upgrade head`（空库）
- [ ] 手工验证（说明还差什么）

## 风险 / 未验证
- ...
```

规则：

- 至少另一名人类 review；关键路径（认证、权限、私密脱敏、时区、迁移、冲突、提醒）两人都 review。
- 不允许自审自并；AI 不能给“验收通过”的结论。
- reviewer 要自己跑命令、看测试、检查有没有超范围，而不是只看描述。

### 9.7 合并后

```bash
git switch main
git pull
git branch -d feat/db-users-teams
```

## 10. 提交与协作约定（摘要）

提交信息用中文 + Conventional Commits：

```text
feat(auth): 支持用户名密码注册 (AUTH-1)
fix(event): 冲突检测排除 declined (EVT-11)
test(conflict): 覆盖全天与跨天冲突
docs(dev): 补充 WSL 环境搭建
chore(ci): 缓存 pnpm store
```

- 一个提交只做一件事；不混格式化。
- 不合入未通过的测试；不提交注释掉的大段代码。
- 不 force push `main`；不自行打 tag/改版本号。
- 需求/契约变更走 CR；架构决策写 ADR（见 [变更控制](../ai/04-变更控制与追踪.md)）。

## 11. 常见故障

| 现象 | 原因 | 处理 |
|---|---|---|
| `make: command not found` | 没装 make | 装 GNU Make，或按 5.2 手动安装 |
| Windows `make` 报 `'[' 不是内部或外部命令` | recipe 走了 cmd，不是 sh | 把 Git 的 `bin` 加入 PATH，或用手动命令 |
| macOS `make` 报 `ifeq` 相关错误 | 系统 make 是 BSD make | `brew install make` 后用 `gmake` |
| 导入 `app.config` 报 `secret_key Field required` | `.env` 缺失/不在仓库根目录 | `cp .env.example .env` 并填 `SECRET_KEY` |
| `ModuleNotFoundError: No module named 'app'` | 没在 `server/` 下运行 | `cd server` 或用 `make` |
| `alembic: command not found` | 没激活 venv | 用 `python -m alembic`（venv 内） |
| `server/.venv belongs to another platform` | 跨平台复用了 venv | 删除 `server/.venv` 后重装 |
| `Cannot find module '../rolldown-binding.linux-x64-gnu.node'` | `node_modules` 是另一平台装的 | 删除 `node_modules` 后重装，或切回原平台 |
| `ERR_PNPM_STORE_DIR_OPEN_OPERATION_LOCK` / `Read-only file system` | 仓库在 `/mnt/*` 跨文件系统，pnpm 锁失败 | 把仓库移到 Linux 文件系统；或 `pnpm config set store-dir ~/.local/share/pnpm/store` 后重试 |
| `EADDRINUSE` / 端口被占用 | 残留 uvicorn/vite | 按第 7 节找 PID 并结束，或换端口（换后端端口要同步改 Vite 代理） |
| `database is locked` | 多个后端进程写同一个 SQLite | 只保留一个后端；确认没有残留进程；必要时重启 |
| CORS 报错 | 直连 8000，来源不在白名单 | 开发期用 5173 的 Vite 代理；或把来源加进 `CORS_ORIGINS` 并重启 |
| 迁移日志中文乱码 | Windows 控制台编码 | `chcp 65001`，或 `$env:PYTHONUTF8=1` |
| `pnpm install --frozen-lockfile` 失败 | 改了 `package.json` 没更新锁文件 | 本地 `pnpm install` 后提交 `pnpm-lock.yaml` |
| 页面显示“后端 未连接” | 后端没起、端口不对、代理目标不对 | 先 `curl /health`，再检查 `vite.config.ts` 与终端报错 |

## 13. 遇到问题怎么问

提问时带上：

- 你想做什么（关联需求编号/任务）；
- 完整命令；
- 完整报错（不要只截最后一行）；
- 操作系统与版本（Windows / WSL / macOS，`python --version`、`node -v`、`pnpm -v`）；
- 已经试过什么。

不要发 `.env` 内容、token、密码或数据库文件。需要贴配置时，用 `.env.example` 或把值打码。
