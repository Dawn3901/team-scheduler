### 3.2 R-02 400/422 契约冲突

**证据**（同一件事四处不同说法）

| 位置 | 说法 |
|---|---|
| `server/app/errors.py:52-66` | `RequestValidationError` → **400** `VALIDATION_ERROR` |
| `docs/02` UC-01 2b（`:141`）、AUTH-1 示例（`:381`） | 密码过短 → **422** |
| `docs/03` 注册接口（`:401`） | 错误 `422 VALIDATION_ERROR` |
| `docs/03` 错误码表（`:687`） | **400** `VALIDATION_ERROR` |
| `docs/ai/02` 错误码表（`:128`） | **400** `VALIDATION_ERROR` |
| `docs/ai/02` 契约测试矩阵（`:383`） | 401/403/404/409/**422** 各至少 1 条 |

**影响**

- AUTH-1 的验收标准（密码 < 8 位返回 422）当前实现无法满足。
- 前端按状态码/错误码分支时行为不确定；契约测试无法编写。
- 违反“不得静默改契约”，必须在写认证前定案。

**建议**

走 CR 二选一（推荐 A）：

- **A. 区分“格式错误”和“语义错误”**：JSON 解析/类型错误 → 400 `VALIDATION_ERROR`；业务语义（密码长度、结束≤开始、非成员参与者）→ 422 + 具体 code（`INVALID_TIME_RANGE` 等）。这最贴近 PRD 用例。
- **B. 全部统一 400**：同步修改 `docs/02` 的 422 描述、`docs/03:401`、`docs/ai/02` 测试矩阵，并说明理由。

无论选哪个，都要：更新三份文档 → 改 handler/service → 补 400/422 契约测试 → 两人 review。

**验收**：`docs/02`、`docs/03`、`docs/ai/02` 对同一场景只出现一种状态码；测试覆盖两种分支。

### 3.3 R-03 错误码映射不完整

**证据**

```python
# server/app/errors.py:13-21
HTTP_ERROR_CODES = {
    400: "VALIDATION_ERROR",
    401: "UNAUTHORIZED",
    403: "FORBIDDEN",
    404: "NOT_FOUND",
    405: "METHOD_NOT_ALLOWED",
    429: "RATE_LIMITED",
    500: "INTERNAL_ERROR",
}
```

`docs/ai/02:128-144` 还定义了 409（`USERNAME_TAKEN`、`INVITE_CODE_INVALID`、`TIME_CONFLICT`、`EVENT_CANCELLED`、`EVENT_ENDED`）与 422（`INVALID_TIME_RANGE` 等）。当前如果路由写 `raise HTTPException(status_code=409, detail=...)`，handler 会走到 `HTTP_ERROR_CODES.get(409, "HTTP_ERROR")`，前端收到 `HTTP_ERROR`，与契约不符。

**建议**

- 领域错误统一 `raise ApiError(409, "TIME_CONFLICT", "...", details=...)`，不要用裸 `HTTPException` 表达业务语义。
- 给 409/422 增加兜底映射（如 `CONFLICT` / `UNPROCESSABLE_ENTITY`），或者对未映射状态码直接断言失败，避免静默降级。
- 增加参数化测试：按 `docs/ai/02` 的错误码表逐个构造，断言 `status + code + body shape`。
- 在 `docs/dev/01` 已注明该约束；实现时不要只改一处。

**验收**：错误码表里的每个 code 都有办法产生且被测试覆盖；不存在未声明的 `HTTP_ERROR` 出现在业务响应里。

### 3.4 R-04 405 缺少 `Allow` 头

**证据**（实测）

```http
HTTP/1.1 405 Method Not Allowed
content-length: 73
vary: Origin

{"code":"METHOD_NOT_ALLOWED","message":"Method Not Allowed","details":{}}
```

没有 `Allow: GET`。原因：

```python
# server/app/errors.py:68-71
return JSONResponse(status_code=exc.status_code, content=error_body(code, str(exc.detail)))
```

没有传 `exc.headers`。401 将来也会丢 `WWW-Authenticate`，429 会丢 `Retry-After`。

**建议**：`JSONResponse(..., headers=exc.headers)`；补 405 的 `Allow` 断言。另外 `message` 目前是英文（`str(exc.detail)`），产品 UI 是中文，建议同时把默认文案映射为中文（与 R-12 一起做）。

### 3.5 R-05 健康检查 503 不走统一错误体

**证据**

```python
# server/app/routers/health.py:18-22
try:
    db.execute(text("SELECT 1"))
except SQLAlchemyError:
    return JSONResponse(status_code=503, content={"status": "error", "db": "error"})
```

- `docs/02` OPS-1 只规定“DB 不可用返回 503”，没说 body；`docs/03:1395` 也只写成功体。
- 共享类型 `HealthStatus` 期望 `{status,db}`，所以前端能解析；但 503 与全局错误体不一致，监控/网关可能按 `code` 解析。
- 该分支没有任何测试（无法确认 503 时连接是否已坏、health 是否还可用）。

**建议**：明确 health 是“基础设施接口，豁免统一错误体”，写进 `docs/ai/02`；补一条用依赖覆盖/坏 DB 触发 503 的测试。若选择统一错误体，则同步改 `HealthStatus` 与前端。

### 3.8 R-08 CI 与依赖可复现性

**证据**

- `.github/workflows/ci.yml` 固定 `pnpm 12.11.2`，根 `package.json` 没有 `packageManager`；本地用其他 pnpm 版本时锁文件行为可能不同。
- Python 依赖只有下限（`fastapi>=0.115` 等），没有 constraints/lock；CI 与本地可能装到不同版本。
- workflow 没有 `permissions`（默认 token 权限可能偏大）、没有 `concurrency` 取消旧任务、没有缓存 pip。
- 后端 job 顺序是 ruff → pytest → alembic；迁移只在测试后跑一次，且不是空库验证。

**建议**：

- 根 `package.json` 加 `"packageManager": "pnpm@12.11.2"`，CI 用 Corepack 读取；或统一用 `pnpm/action-setup` 的 `package_json` 模式。
- 加 `permissions: contents: read` 与 `concurrency`。
- 迁移在测试前对空库跑一遍；后续加 `alembic check` 或迁移测试。
- 依赖锁定方案（constraints / uv / pip-tools）属于工具选型，先组内确认再引入。
- 覆盖率门禁可放到 W5，但先把“契约测试矩阵”补齐。

### 3.9 R-09 SQLite 相对路径依赖启动目录

**证据**

```python
# config.py
database_url: str = "sqlite:///./data/teamsync.db"
# db.py
engine = create_engine(settings.database_url, ...)
```

`.env` 在仓库根目录，但 `make` 全部 `cd server` 后启动；若开发者用 `uvicorn --app-dir server app.main:app`（或让 IDE 以仓库根为工作目录）启动，会在根目录创建 `data/teamsync.db`，与 `server/data/teamsync.db` 不是同一个库。表现是“迁移过了但接口说没表”或“数据莫名消失”。

**建议**：在 `config.py` 里把相对 SQLite 路径解析为相对 `server/`（或仓库根）的绝对路径；或在 `db.py` 启动时打印实际数据库路径。加一条测试/启动日志，避免静默分叉。

### 3.10 R-10 Token 存储与安全头

**证据**：`client.ts` 用 `localStorage` 存 JWT；`docs/03:1280` 明确接受该取舍（P1 可换 httpOnly cookie），但 `main.py` 目前没有 CSP、`X-Content-Type-Options`、`Referrer-Policy`、`frame-ancestors` 等头。

**建议**：认证功能上线前，至少加：

- `Content-Security-Policy`（先 report-only，再收紧）；
- `X-Content-Type-Options: nosniff`；
- `Referrer-Policy: no-referrer`；
- 若不需要被嵌入，`frame-ancestors 'none'`。

并在 `docs/03` 的安全章节记录“localStorage + CSP”的组合风险与验收方式。不要把 token 写进日志/错误详情。

### 3.11 R-11 前端请求健壮性

**证据**：`request()` 没有 `AbortSignal`/超时；收到 401 只抛 `ApiError`，不清理 token/跳登录；无论 method 都设置 `Content-Type: application/json`（GET 也会带，跨域时可能触发不必要的预检）；`App.tsx` 的健康检查没有超时，后端挂起时永远显示“检查中…”。
